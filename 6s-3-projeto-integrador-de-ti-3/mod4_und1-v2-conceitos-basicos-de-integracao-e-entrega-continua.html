📈 Desenvolvimento atual: desafios e evolução

Nos últimos anos, sistemas de software têm evoluído significativamente em tamanho, complexidade e importância estratégica. Os processos de desenvolvimento também se tornaram mais dinâmicos, visando entregas rápidas e contínuas. Nesse cenário, é comum que existam diversos times trabalhando em partes que precisam ser integradas e entregues de forma coordenada.

history Contexto histórico:

Historicamente, organizações eram divididas em departamentos de Desenvolvimento (Dev) e Suporte/Operações (Ops). Essa divisão gerava muitos desafios:

  • 🔴 Desenvolvedores entregavam código sem considerar o ambiente de produção
  • 🔴 Operações rejeitavam entregas por falta de documentação ou confiabilidade
  • 🔴 Ciclos de release longos (semanas ou meses)
  • 🔴 Retrabalho constante e baixa qualidade

group DevOps: a união entre Dev e Ops

DevOps é um conceito que surgiu com o objetivo de agilizar a implantação de sistemas a partir da união do desenvolvimento (Dev) e operações (Ops). A ideia é fazer com que profissionais de ambas as áreas trabalhem em conjunto desde o início do processo para realizar entregas mais rápidas e confiáveis.

target Objetivos do DevOps

  • 🎯 Criar um processo repetível e confiável para entrega
  • 🎯 Automatizar tudo que for possível (build, testes, deploy)
  • 🎯 Manter tudo em um sistema de controle de versões (Git)
  • 🎯 Se um passo causa dor, executar com mais frequência e o quanto antes
  • 🎯 "Concluído" significa pronto para entrega
  • 🎯 Todos são responsáveis pela entrega do software

🔄 CI/CD: Integração e Entrega Contínua

CI (Continuous Integration) e CD (Continuous Delivery / Continuous Deployment) são práticas que permitem automação e monitoramento contínuo do ciclo de vida de aplicações. Ambas são usadas em times ágeis com práticas de DevOps, ajudando times de desenvolvimento, segurança e operação a serem mais eficientes e efetivos.

CI Integração Contínua (Continuous Integration)

Integração Contínua é uma prática de integração de mudanças de código em uma branch principal (ou estável) que é compartilhada e frequentemente recebe alterações. Essa técnica permite a identificação fácil e rápida de problemas para que desenvolvedores possam corrigi-los antes de serem integrados.

checklist Principais atividades da CI:

  • ✅ Verificação se o build ocorre normalmente (sem erros de compilação/sintaxe)
  • ✅ Execução de testes automatizados (unitários, integração, cobertura)
  • ✅ Verificação de conformidade de padrões (linter, formatação)
  • ✅ Identificação de problemas ou ameaças conhecidas (vulnerabilidades)
  • ✅ Geração de artefatos (binários, pacotes) para os próximos estágios

github Exemplo de CI com GitHub Actions (Cidade Virtual)

name: CI - Testes e Validação

on:
  push:
    branches: [ develop, main ]
  pull_request:
    branches: [ main ]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Setup Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '18'
      - name: Instalar dependências
        run: npm ci
      - name: Executar linter
        run: npm run lint
      - name: Executar testes unitários
        run: npm test -- --coverage
      - name: Verificar dependências vulneráveis
        run: npm audit --production

Fluxo: A cada push ou pull request, o GitHub Actions automaticamente executa linter, testes e verificação de segurança. Se falhar, o PR é bloqueado.

CD Entrega Contínua (Continuous Delivery / Deployment)

CD é uma prática que trabalha em conjunto com CI para automatização da provisão de infraestrutura e lançamento de versões. Com CD podemos automatizar o lançamento de versões assim que novas versões são finalizadas.

package Continuous Delivery

Cada alteração aprovada é automaticamente preparada para produção, mas o deploy exige aprovação manual (ex: clicar em um botão).

Ideal para: Projetos com requisitos regulatórios, compliance, ou que exigem validação final.

rocket_launch Continuous Deployment

Cada alteração aprovada é automaticamente implantada em produção sem intervenção manual.

Ideal para: Projetos com alta confiança em testes automatizados, equipes maduras em DevOps.

warning Importante:

Diferentemente de CI, a entrega é frequentemente aplicada somente a marcos específicos, por exemplo, major releases. Portanto, é necessário adotar uma política de lançamentos claras, assim como marcações (tags, flags) para automação do processo.

cloud_upload Exemplo de CD com GitHub Actions (Cidade Virtual)

name: CD - Deploy para Vercel

on:
  push:
    branches: [ main ]

jobs:
  deploy:
    runs-on: ubuntu-latest
    needs: [build-and-test]  # depende do CI passar
    steps:
      - uses: actions/checkout@v3
      - name: Deploy para Vercel
        uses: amondnet/vercel-action@v20
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-org-id: ${{ secrets.ORG_ID }}
          vercel-project-id: ${{ secrets.PROJECT_ID }}
          vercel-args: '--prod'

Fluxo: Quando um PR é aprovado e mesclado na branch `main`, o CD automaticamente implanta a nova versão no ambiente de produção (Vercel).

📦 Importância do controle de versões para CI/CD

Sistemas e políticas de controle de versão constituem parte importante no processo de CI e CD. Atualmente, existem diversas ferramentas e plataformas que oferecem mecanismos críticos para a prática de controle de versões, como GitHub, GitLab, Bitbucket, entre outras.

account_tree

Git Flow (tradicional)

Branches: main, develop, feature/*, release/*, hotfix/*

Vantagem: Muito estruturado, ideal para releases programadas.
Desvantagem: Pode ser complexo para times pequenos.

linear_scale

GitHub Flow (simplificado)

Branches: main + feature/* (com PR)

Vantagem: Simples, ideal para CD.
Desvantagem: Menos adequado para múltiplas versões simultâneas.

tips_and_updates Recomendação para projetos individuais ou pequenos

Adote uma abordagem simplificada do GitHub Flow:

  • main → produção (sempre estável)
  • develop → homologação (pode conter features em integração)
  • feature/nome → desenvolvimento de nova funcionalidade
  • hotfix/nome → correção crítica em produção

Independente da política de trabalho (feature ou trunk-based branches), CI/CD podem trazer muitos benefícios para o processo.

🔁 Visão Integradora Aplicada - Por onde começar no Cidade Virtual?

lightbulb Questões importantes sobre CI/CD:
  • Integração contínua não é apenas uma questão técnica, mas uma mudança cultural e colaborativa em equipes.
  • Inicialmente, pode aumentar a complexidade na configuração inicial e no monitoramento.
  • Tem o potencial para melhoria contínua de processos, aprendizado e qualidade.
  • Atualmente, soluções de IA têm surgido para complementação do processo, como revisão de código automatizada (ex: GitHub Copilot, CodeRabbit).

map Como ser ágil? (projeto solo)

  • 🎯 Foco na entrega de incrementos pequenos e relevantes → entregar uma funcionalidade por vez, não tudo de uma vez
  • 🔄 Integrar mudanças e entregar valor assim que possível → CI/CD ajuda exatamente nisso
  • 📢 Coletar feedbacks rapidamente para eventuais correções (comunidade, tutor)
1

Entenda seu processo atual

Quais práticas e processos você usa atualmente? (Commits manuais, testes locais, deploy manual na Vercel?)

2

Identifique o que pode ser automatizado

Automatizar builds, testes unitários, linting e deploy (pelo menos para homologação).

3

Comece pequeno e evolua

Não busque implantar o processo completo de uma vez. Comece com pequenas automações e evolua!

4

Automatize builds e testes simples primeiro

Foque inicialmente na automação de construções (builds) e testes simples (unitários). Depois avance para testes de integração e E2E.

5

Defina padrões e processos simples

Defina padrões e processos simples que possam ser facilmente absorvidos e apresentem alto valor. Ex: "toda PR precisa ter testes passando" ou "deploy automático apenas na branch main".

rocket Roadmap de implementação CI/CD para o Cidade Virtual (projeto solo)

  • Semana 1: Configurar GitHub Actions para rodar linter e testes unitários a cada push na `develop`
  • Semana 2: Adicionar verificação de cobertura de código (70% mínima) e `npm audit`
  • Semana 3: Configurar deploy automático para homologação (Vercel preview) ao criar PR
  • Semana 4: Configurar deploy automático para produção ao fazer merge na `main` (após aprovação manual dos testes de aceitação)
