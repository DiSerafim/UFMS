🐞 Defeitos no Desenvolvimento de Software

Defeitos (ou bugs) são falhas presentes nos artefatos de software que podem causar comportamentos inesperados ou incorretos durante a execução do sistema. Compreender suas causas é o primeiro passo para evitá-los.

error Principais causas de defeitos:
  • Tradução incorreta de informações – ao extrair requisitos do cliente ou do ambiente, informações são interpretadas erroneamente.
  • Origem humana – a maioria dos defeitos decorre de falhas de comunicação, cansaço, falta de conhecimento ou suposições incorretas.
  • Complexidade acidental – soluções desnecessariamente complexas introduzem mais pontos de falha.

real_estate_agent Exemplo real - Cidade Virtual

Durante o levantamento de requisitos com comerciantes do bairro Cabanagem, a seguinte situação ocorreu:

Fala do comerciante: "Eu quero que as pessoas vejam meus horários de funcionamento."

Tradução incorreta (defeito): A equipe interpretou que deveria criar um campo "horario_funcionamento" no banco, mas não considerou que muitos comerciantes têm horários diferentes por dia da semana (ex: seg-sex 8h-18h, sábado 8h-12h).

Consequência: O sistema inicial não permitia configurar horários variados, gerando insatisfação.

Lição: A validação com o usuário durante a verificação dos requisitos teria evitado esse retrabalho.

attach_money Custo do defeito ao longo do tempo

Quanto mais tarde um defeito é descoberto, maior o custo para corrigi-lo. Um defeito identificado na fase de requisitos pode custar 1x; na implementação, 10x; em produção, até 100x ou mais. Por isso, inspeções e revisões precoces são essenciais.

📋 Revisão de Artefatos (projeto e código)

A revisão é um processo de verificação que pode ser conduzido de forma informal ou formal. Seu principal objetivo é identificar defeitos precocemente, antes que eles avancem para fases posteriores do desenvolvimento.

Tipos de Revisão

chat Revisão Informal

Exemplo: Dois desenvolvedores sentam juntos para analisar um trecho de código antes do commit.

Vantagem: Rápida, baixo custo.

Desvantagem: Depende da habilidade do revisor.

group Revisão por Pares (Peer Review)

Exemplo: Um pull request no GitHub é revisado por outro membro da equipe antes de ser mesclado.

Vantagem: Combina conhecimento da equipe.

Ferramenta: GitHub, GitLab, Bitbucket.

assignment Revisão Técnica Formal (FTR)

Exemplo: Reunião agendada com papeis definidos (autor, revisor, moderador, secretário) para avaliar o DER do sistema.

Vantagem: Resultados documentados, rastreáveis.

code Exemplo de Revisão de Código - Cidade Virtual

Código original (com possível defeito):

function calcularAvaliacaoMedia(avaliacoes) {
    let soma = 0;
    for (let i = 0; i <= avaliacoes.length; i++) { // ERRO: <= causa undefined
        soma += avaliacoes[i];
    }
    return soma / avaliacoes.length;
}

Comentário do revisor (pull request): "A condição do loop está errada. Quando i == avaliacoes.length, avaliacoes[i] é undefined. Corrigir para i < avaliacoes.length."

Código corrigido:

function calcularAvaliacaoMedia(avaliacoes) {
    if (!avaliacoes || avaliacoes.length === 0) return 0;
    let soma = 0;
    for (let i = 0; i < avaliacoes.length; i++) {
        soma += avaliacoes[i];
    }
    return soma / avaliacoes.length;
}

Resultado: Defeito identificado antes de chegar à produção. Custo de correção: mínimo.

lightbulb Checklist para Revisão de Código (Cidade Virtual)

  • ✅ As variáveis têm nomes significativos? (ex: "avaliacoes" ao invés de "arr")
  • ✅ Há tratamento para casos de borda (lista vazia, valores nulos)?
  • ✅ A lógica está correta para todos os cenários possíveis?
  • ✅ O código segue o estilo definido pela equipe (linter configurado)?
  • ✅ Não há código duplicado ou "dead code"?
  • ✅ As funções são pequenas e fazem apenas uma coisa?

🔬 Inspeção de Artefatos (projeto e código)

A inspeção é uma técnica de verificação mais rigorosa e estruturada que a revisão comum. Foi formalizada por Michael Fagan na IBM nos anos 1970 e provou ser extremamente eficaz na remoção precoce de defeitos.

group_work Papéis na Inspeção Fagan
  • Autor: Criador do artefato (não participa ativamente da inspeção, mas responde a perguntas).
  • Moderador: Lidera a reunião, garante que o processo seja seguido.
  • Leitor: Apresenta o artefato linha por linha durante a reunião.
  • Testador: Foca em cenários de teste e possíveis falhas.
  • Secretário: Registra os defeitos encontrados.

Etapas do Processo de Inspeção

1

Planejamento

Moderador seleciona o artefato, convida os inspetores (3 a 5 pessoas) e distribui o material com antecedência.

2

Preparação Individual

Cada inspetor estuda o artefato de forma independente, anotando possíveis defeitos e dúvidas.

⏱️ Dica: A preparação individual é a etapa mais importante. Recomenda-se de 1 a 2 horas de estudo prévio.
3

Reunião de Inspeção

O leitor apresenta o artefato. Os inspetores apontam defeitos, que são registrados pelo secretário. O autor esclarece dúvidas.

4

Correção

O autor corrige os defeitos identificados.

5

Verificação (Follow-up)

O moderador verifica se todas as correções foram realizadas adequadamente.

fact_check Exemplo de Inspeção - DER do Cidade Virtual

Artefato inspecionado: Diagrama Entidade-Relacionamento (DER) – versão inicial.

Defeitos encontrados durante a inspeção:

  • Defeito #1: A entidade COMERCIO estava diretamente ligada a USUARIO, mas não havia suporte para múltiplos telefones de contato. → Solução: Criar entidade TELEFONE (1:N).
  • Defeito #2: Campo "avaliacao_media" em COMERCIO seria atualizado manualmente, mas deveria ser calculado automaticamente a partir das avaliações. → Solução: Remover campo calculado, criar visão (view) no banco.
  • Defeito #3: Não havia relacionamento entre EVENTO e USUARIO (quem criou o evento). → Solução: Adicionar chave estrangeira "criado_por" em EVENTO.

Resultado: 3 defeitos críticos identificados antes da codificação. Economia estimada: 40 horas de retrabalho.

trending_up Eficácia da Inspeção

Estudos mostram que inspeções podem remover 60% a 90% dos defeitos antes mesmo da execução do primeiro teste. A relação custo-benefício é altamente positiva, especialmente para sistemas críticos ou de longa duração.

Métrica útil: Taxa de defeitos por página (documento) ou por KLOC (código). Para o Cidade Virtual, uma meta razoável é < 1 defeito por 100 linhas de código inspecionado.

⚖️ Inspeção vs Teste: Complementares, não concorrentes

Uma dúvida comum é se a inspeção substitui o teste. A resposta é não. Eles são complementares e encontram diferentes tipos de problemas.

Característica Inspeção (Revisão estruturada) Teste (Execução)
Natureza Estática (não executa o código) Dinâmica (executa o código)
Encontra Defeitos de lógica, omissões, inconsistências, violação de padrões Falhas de execução, erros de desempenho, problemas de integração
Requer Apenas o artefato (documento, código, diagrama) Ambiente de execução, dados de teste, oráculo
Momento ideal Antes da execução dos testes Após a codificação
Exemplo Cidade Virtual Inspecionar a lógica de cálculo da avaliação média no código antes de rodar os testes Executar o teste unitário que valida o cálculo da avaliação média
sync Combinação poderosa:

Use a inspeção para remover defeitos estruturais e de lógica precocemente. Use os testes para verificar comportamento dinâmico e detectar defeitos residuais. Juntas, essas técnicas aumentam drasticamente a confiabilidade do software.

🚀 Técnicas Avançadas e Recomendações para Projetos de Extensão

checklist Inspeção Baseada em Checklist

Crie checklists específicos para cada tipo de artefato. Exemplo para o DER do Cidade Virtual:

  • ☐ Cada entidade tem um identificador único (chave primária)?
  • ☐ Todos os relacionamentos 1:N têm a chave estrangeira no lado correto?
  • ☐ Os tipos de dados são adequados (datas, valores monetários, textos longos)?
  • ☐ Há campos calculados que deveriam ser removidos?
  • ☐ As restrições de integridade referencial estão definidas?

person_search Inspeção por Cenários (Scenario-based)

Em vez de inspecionar genericamente, use cenários de uso real. Exemplo: "Um comerciante tenta cadastrar seu negócio, mas esquece de preencher o telefone. O sistema deve impedir o cadastro e exibir uma mensagem amigável."

Esse tipo de inspeção é particularmente eficaz para encontrar defeitos de usabilidade e completude funcional.

analytics Análise Estática Automatizada

Ferramentas como ESLint (JavaScript), SonarQube, Pylint (Python) realizam inspeção automática do código, detectando violações de estilo, código morto, complexidade ciclomática elevada e potenciais bugs.

Para o Cidade Virtual: Configure ESLint com regras recomendadas e integre ao GitHub Actions. Cada pull request será inspecionado automaticamente.

emoji_objects Insight para Projetos de Extensão Universitária

Em projetos comunitários, a inspeção participativa pode incluir usuários leigos? Sim, mas com adaptações. Realize walkthroughs com moradores e comerciantes: apresente o protótipo e peça que eles "percorram" cenários. Eles não precisam conhecer técnicas formais – sua visão de negócio é valiosa para validar requisitos e identificar omissões.

Exemplo prático: Mostre a tela de cadastro de comércio para Dona Maria (doceira) e pergunte: "O que falta aqui para você conseguir divulgar seus produtos?" Ela pode sugerir campos como "possui entrega?" ou "aceita PIX?".

🌍 Inspeção e Revisão na Extensão Universitária

A extensão universitária exige não apenas entregar um software funcional, mas também formar cidadãos críticos e engajar a comunidade. As práticas de inspeção e revisão, quando adaptadas, podem envolver ativamente os usuários finais.

diversity_3 Co-criação

Inspeções com comerciantes validam se os requisitos realmente atendem às necessidades do bairro.

school Aprendizado

Revisões técnicas ensinam boas práticas para a equipe e para a comunidade (alfabetização digital).

gavel Transparência

Artefatos revisados e inspecionados geram confiança e credibilidade no projeto de extensão.

group Como envolver a comunidade na inspeção?

Modelo adaptado para o Cidade Virtual:

  • Inspeção de requisitos: Reunião com 3 comerciantes e 3 moradores para validar as histórias de usuário.
  • Inspeção do protótipo (walkthrough): Sessão de 1 hora onde os usuários "navegam" pelo protótipo no Figma, apontando dificuldades e omissões.
  • Revisão de usabilidade: Após o desenvolvimento, convide os mesmos usuários para testar o sistema em produção (ambiente de homologação).

Resultado: Defeitos de interpretação (ex: "achei que o campo 'descrição' seria para o endereço") são corrigidos antes do lançamento oficial.

✍️ Exercício de Fixação - Inspeção e Revisão no Cidade Virtual

quiz Cenário prático

Você é o moderador de uma inspeção no projeto Cidade Virtual. Responda:

  1. Qual a diferença principal entre uma revisão informal por pares e uma inspeção formal Fagan?
  2. Durante a inspeção do DER, foi encontrado que a entidade "AVALIACAO" não possui relação com "USUARIO" (quem avaliou). Que tipo de defeito é esse? Como corrigir?
  3. Que técnica de inspeção você recomendaria para validar se os cenários de uso (ex: "buscar comércio por categoria") estão completos?
  4. Como você adaptaria o processo de inspeção para envolver um comerciante leigo em tecnologia?
🔎 Ver sugestão de respostas

1. A revisão informal não segue um processo estruturado (pode ser apenas uma conversa entre dois desenvolvedores). A inspeção formal tem papéis definidos, preparação individual, reunião com registro de defeitos e follow-up.

2. Defeito de omissão (falta de relacionamento necessário). Corrigir adicionando chave estrangeira "usuario_id" na tabela AVALIACAO, referenciando USUARIO(id).

3. Inspeção por cenários (scenario-based inspection), onde cada cenário de uso é percorrido no artefato para verificar se todas as etapas estão cobertas.

4. Realizar um walkthrough (reunião guiada) em vez de uma inspeção formal. Apresente o protótipo ou documento de forma visual, faça perguntas abertas ("O que aconteceria se...") e evite jargões técnicos.
