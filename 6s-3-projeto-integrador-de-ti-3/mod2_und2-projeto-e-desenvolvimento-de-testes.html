📖 Estudo de caso: FACOFFEE

Para entender na prática como aplicar testes de software, vamos analisar o estudo de caso FACOFFEE, uma aplicação web desenvolvida para auxiliar na divisão dos custos do consumo de café e manutenção da máquina na copa da Faculdade de Computação da UFMS (FACOM/UFMS).

coffee FACOFFEE - Características

A aplicação foi concebida como parte do processo de ensino de conceitos e técnicas avançadas de desenvolvimento, incluindo:

  • Programação Funcional - paradigma declarativo para transformações de dados
  • Domain Driven Design (DDD) - modelagem focada no domínio do negócio
  • Arquiteturas Baseadas em Serviços - microsserviços e API-first

Principais funcionalidades:

  • ✅ Gestão de usuários (servidores docentes e técnicos)
  • ✅ Autenticação e autorização (login com e-mail institucional)
  • ✅ Gestão de planos de consumo (café, leite, adoçante, etc.)
  • ✅ Gestão de assinaturas (adesão e cancelamento)
  • ✅ Gestão de pagamentos (envio de comprovantes e conciliação)

Repositório: https://github.com/hsborges/facoffee-api

lightbulb Relação com o Cidade Virtual

Assim como o FACOFFEE, o Cidade Virtual também possui funcionalidades similares: gestão de usuários (moradores/comerciantes/autônomos), autenticação, planos de destaque (análogo a planos de consumo) e interações comunitárias. Os aprendizados deste estudo de caso serão diretamente aplicáveis ao seu projeto.

🚀 Por onde começar? Analisando a arquitetura

Antes de escrever qualquer teste, é fundamental entender a arquitetura e os componentes do sistema. No caso do FACOFFEE, a API foi estruturada da seguinte forma:

📁 facoffee-api/
├── 📁 controllers/   → Tratamento de requisições HTTP
├── 📁 entities/      → Abstrações das entidades do domínio
├── 📁 middlewares/   → Interceptações de requisições (autenticação, logs)
├── 📁 services/      → Atividades do negócio (regras de negócio)
├── 📁 tasks/         → Scripts com procedimentos auxiliares (jobs)
└── 📁 utils/         → Funções utilitárias (formatação, validação)
code

Alto impacto no negócio

/services e /controllers contêm a lógica crítica que merece mais atenção nos testes.

build

Baixo impacto / utilitários

/utils e /tasks podem ter testes mais simples ou até serem priorizados depois.

architecture Adaptando para o Cidade Virtual

🎭 Isolando unidades: Stubs, Mocks e Spies

Em testes unitários, muitas vezes uma unidade depende de outras (banco de dados, API externa, sistema de arquivos). Para isolar a unidade sob teste, usamos mocks que simulam o comportamento das dependências.

block Exemplo: OperacaoService depende de FileService

No FACOFFEE, o serviço que processa comprovantes de pagamento depende de um serviço de arquivos. Podemos criar um mock para simular esse componente:

// OperacaoService.js (código original)
class OperacaoService {
    constructor(fileService) {
        this.fileService = fileService;
    }
    
    async processarComprovante(comprovantePath) {
        const existe = await this.fileService.existe(comprovantePath);
        if (!existe) throw new Error('Arquivo não encontrado');
        
        const conteudo = await this.fileService.ler(comprovantePath);
        // ... processamento do comprovante
        return { status: 'processado', dados: conteudo };
    }
}

// Teste com mock (Jest)
describe('OperacaoService', () => {
    let mockFileService;
    let operacaoService;
    
    beforeEach(() => {
        // Criando mock do FileService
        mockFileService = {
            existe: jest.fn(),
            ler: jest.fn()
        };
        operacaoService = new OperacaoService(mockFileService);
    });
    
    test('deve processar comprovante com sucesso', async () => {
        // Configurando o mock
        mockFileService.existe.mockResolvedValue(true);
        mockFileService.ler.mockResolvedValue('conteudo_do_arquivo');
        
        const resultado = await operacaoService.processarComprovante('/tmp/comprovante.pdf');
        
        expect(resultado.status).toBe('processado');
        expect(mockFileService.existe).toHaveBeenCalledWith('/tmp/comprovante.pdf');
        expect(mockFileService.ler).toHaveBeenCalledTimes(1);
    });
    
    test('deve lançar erro se arquivo não existe', async () => {
        mockFileService.existe.mockResolvedValue(false);
        
        await expect(operacaoService.processarComprovante('/tmp/inexistente.pdf'))
            .rejects.toThrow('Arquivo não encontrado');
    });
});

cached Aplicação no Cidade Virtual

Cenário: Serviço de cálculo de avaliação média que depende de um repositório de avaliações.

// AvaliacaoService.js
class AvaliacaoService {
    constructor(avaliacaoRepository) {
        this.avaliacaoRepository = avaliacaoRepository;
    }
    
    async calcularMediaPorComercio(comercioId) {
        const avaliacoes = await this.avaliacaoRepository.buscarPorComercio(comercioId);
        if (!avaliacoes || avaliacoes.length === 0) return 0;
        const soma = avaliacoes.reduce((acc, a) => acc + a.nota, 0);
        return soma / avaliacoes.length;
    }
}

// Teste com mock do repositório
test('calcularMediaPorComercio deve retornar média correta', async () => {
    const mockRepo = {
        buscarPorComercio: jest.fn().mockResolvedValue([{ nota: 5 }, { nota: 4 }, { nota: 3 }])
    };
    const service = new AvaliacaoService(mockRepo);
    
    const media = await service.calcularMediaPorComercio('comercio123');
    
    expect(media).toBe(4.0);
    expect(mockRepo.buscarPorComercio).toHaveBeenCalledWith('comercio123');
});

🔗 Testes de integração - Estratégias

Testes de integração verificam o comportamento dos componentes de forma integrada. Existem duas estratégias principais:

arrow_downward

Bottom-up

Começa pelos componentes de nível mais baixo (ex: repositórios) e sobe para níveis mais altos (controllers).

Vantagem: Isolamento gradual.

arrow_upward

Top-down

Começa pelos componentes de nível mais alto (ex: endpoints de API) e usa mocks para os níveis inferiores.

Vantagem: Interface do sistema testada primeiro.

api Teste de integração no FACOFFEE (top-down)

// Teste de integração do endpoint de criação de usuário
const request = require('supertest');
const app = require('../src/app');

describe('POST /api/users', () => {
    test('deve criar usuário com dados válidos', async () => {
        const novoUsuario = {
            nome: "João Silva",
            email: "joao@facom.ufms.br",
            tipo: "professor"
        };
        
        const response = await request(app)
            .post('/api/users')
            .send(novoUsuario)
            .expect(201);
        
        expect(response.body).toHaveProperty('id');
        expect(response.body.email).toBe('joao@facom.ufms.br');
        
        // Verificar persistência real no banco de testes
        const usuarioSalvo = await db.query('SELECT * FROM users WHERE id = $1', [response.body.id]);
        expect(usuarioSalvo.rows[0].nome).toBe('João Silva');
    });
});

warning Cuidados com testes de integração

  • Use um banco de dados de teste separado do de desenvolvimento
  • Isole cada teste (limpe os dados entre execuções)
  • Testes de integração são mais lentos que unitários - não abuse
  • Priorize os fluxos principais (happy path) e os fluxos de erro mais críticos

🎯 Como avançar estrategicamente?

Em um projeto real, nem tudo precisa ser testado da mesma forma. A estratégia deve considerar o impacto no negócio e a probabilidade de falha.

priority_high Alta prioridade (teste exaustivo)

  • Regras de negócio críticas (ex: cálculo de rateio no FACOFFEE)
  • Fluxos de autenticação e autorização
  • Funcionalidades relacionadas a pagamentos
  • APIs públicas/documentadas

low_priority Baixa prioridade (teste superficial)

  • Componentes de UI simples (botões, links)
  • Funções utilitárias muito simples (ex: formatação de data)
  • Scripts administrativos/jobs
  • Funcionalidades pouco utilizadas

🖥️ Testes de sistema - Componente de UI

O FACOFFEE também possui uma interface web. Como testar componentes de UI?

straighten

Testes unitários de UI

Testar componentes React/Vue isoladamente, simulando props e eventos.

Ferramenta: React Testing Library, Vue Test Utils

cypress

Testes de integração/E2E

Testar fluxos completos no navegador, incluindo interações reais.

Ferramenta: Cypress, Selenium, Playwright

react_app Exemplo: teste de componente React (Cidade Virtual)

// Componente: BotaoBusca.jsx
function BotaoBusca({ onClick, desabilitado }) {
    return (
        <button onClick={onClick} disabled={desabilitado} className="btn-busca">
            🔍 Buscar
        </button>
    );
}

// Teste com React Testing Library
import { render, screen, fireEvent } from '@testing-library/react';
import BotaoBusca from './BotaoBusca';

test('deve chamar onClick quando clicado', () => {
    const mockOnClick = jest.fn();
    render(<BotaoBusca onClick={mockOnClick} />);
    
    const botao = screen.getByText('🔍 Buscar');
    fireEvent.click(botao);
    
    expect(mockOnClick).toHaveBeenCalledTimes(1);
});

test('deve estar desabilitado quando prop for true', () => {
    render(<BotaoBusca desabilitado={true} />);
    const botao = screen.getByRole('button');
    
    expect(botao).toBeDisabled();
});

✅ Conclusões e boas práticas

checklist Principais aprendizados do estudo de caso FACOFFEE:
  1. Frameworks de testes ajudam na execução e análise - Invista tempo em aprender Jest, PyTest ou JUnit.
  2. Dependências devem ter seu comportamento simulado - Use mocks para isolar a unidade sob teste.
  3. Nem todas as unidades "merecem" ser testadas - Priorize com base no impacto e risco.
  4. Componentes de alto impacto devem ser priorizados - Services e controllers merecem mais atenção.
  5. Testes de integração ajudam na verificação de comportamentos quando os componentes se comunicam entre si.
  6. Acompanhe a evolução da cobertura - mas sem obsessão: 100% de cobertura não garante ausência de defeitos.

📋 Atividade de Checkout - Plano de Testes

assignment O que você deve entregar:

Você deverá criar um plano de testes para o Cidade Virtual (sistema projetado em PI-I e desenvolvido em PI-II).

tips_and_updates Dicas para a atividade:

  • Comece analisando os artefatos e a arquitetura projetada - Revise o DER, os requisitos e o código existente.
  • Identifique os principais componentes - Models, Controllers, Services, Utils.
  • Defina objetivos de teste - Ex: "garantir que o cálculo da avaliação média esteja correto" ou "validar que o cadastro de comerciantes persiste no banco".
  • Descreva o escopo dos testes - O que será testado (unitário, integração, E2E) e o que NÃO será testado.
  • Proponha estratégias de testes - Caixa branca vs caixa preta, técnicas (classes de equivalência, valor limite).
  • Apresente casos de teste de exemplo - Pelo menos 3 casos completos (entrada, saída esperada, pré-condições).
  • Use diferentes técnicas - Combine classes de equivalência, valor limite, tabela de decisão, etc.

Estrutura sugerida para o Plano de Testes

  1. Introdução e objetivos - O que se pretende alcançar com os testes
  2. Escopo - O que será testado e o que será excluído
  3. Arquitetura e componentes alvo - Mapeamento dos componentes críticos
  4. Estratégias de teste por nível
    • Testes unitários (com técnicas e exemplos)
    • Testes de integração (com exemplos)
    • Testes de sistema/E2E (com exemplos)
  5. Ferramentas selecionadas - Jest, Supertest, Cypress
  6. Métricas e critérios de aceitação - Cobertura mínima, testes passando
  7. Cronograma de implementação - Quando cada tipo de teste será implementado
