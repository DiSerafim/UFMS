📖 Documentação de APIs: O que é e por que é essencial?

A economia global atual é multi-plataforma e conectada por APIs. Plataformas são produtos que podem ser estendidos e usados por terceiros para benefício próprio. Desenvolvedores buscam entender como usar APIs de forma efetiva, e nesse cenário, a documentação se torna um ponto crítico.

description O que é documentação de API?

São documentos técnicos criados e distribuídos pela equipe de desenvolvimento, contendo instruções de como usar efetivamente e integrar com outras APIs. Tratam-se de manuais concisos com toda informação necessária para trabalhar com a API.

Uma boa documentação deve detalhar:

  • ✅ Funções/serviços disponíveis (endpoints)
  • ✅ Estrutura de dados usadas (schemas)
  • ✅ Argumentos necessários (parâmetros, headers, body)
  • ✅ Respostas esperadas (códigos HTTP, exemplos)
  • ✅ Autenticação e autorização (JWT, API keys)
  • ✅ Códigos de erro e seus significados
trending_up Por que documentar APIs?
  • Melhoria da adoção por usuários - API bem documentada é mais fácil de ser integrada
  • Maior conscientização - Equipes entendem limites e capacidades
  • Redução do tempo de suporte e custos - Menos dúvidas repetitivas
  • Melhoria da manutenção - Documentação serve como especificação viva

🔧 OpenAPI e Swagger - Padrões para documentação

A OpenAPI Specification (OAS) é um formato para especificação de APIs REST que pode ser escrita em YAML ou JSON. O Swagger é um conjunto de ferramentas open-source que implementa as especificações do OpenAPI.

openapi: "3.0.0"
info:
  title: "API Cidade Virtual"
  description: "Plataforma para conexão comunitária"
  version: "1.0.0"
servers:
  - url: "https://api.cidadevirtual.vercel.app/v1"
paths:
  /comercios:
    get:
      summary: "Lista comércios"
      parameters:
        - name: "categoria"
          in: "query"
          schema:
            type: "string"
      responses:
        '200':
          description: "Lista de comércios"

🏗️ Estrutura básica do OpenAPI

Uma especificação OpenAPI bem estruturada contém as seguintes seções principais:

info Metadados

Informações sobre a API: título, descrição, versão, contato, licença.

info:
  title: "API Cidade Virtual"
  version: "1.0.0"
  description: "..."]

dns Servidores

Endereços base onde a API está disponível (produção, homologação, desenvolvimento).

servers:
  - url: "https://api.cidadevirtual.vercel.app/v1"
  - url: "http://localhost:3000/api"

route Caminhos (Paths)

Endpoints individuais e seus métodos HTTP (GET, POST, PUT, DELETE).

tune Parâmetros

Query params, path params, headers, body com tipos e validações.

code Schemas

Definições das estruturas de dados (usuário, comércio, avaliação, etc.)

security Segurança

Esquemas de autenticação (JWT, OAuth2, API Key).

📝 Documentação como código (Documentation as Code)

Manter a documentação atualizada pode ser desafiador e, em muitos casos, desenvolvedores acabam sendo negligentes. Processos integrados podem facilitar a atualização, como defendido pela filosofia "documentation as code".

sync_alt Benefícios da documentação como código:
  • ✅ Documentação versionada junto com o código (Git)
  • ✅ Geração automática a partir de anotações/comentários
  • ✅ Redução de inconsistências entre código e documentação
  • ✅ Possibilidade de revisão em pull requests
  • ✅ Ferramentas de CI podem validar a documentação

code Exemplo: Documentação com anotações no Node.js/Express (swagger-jsdoc)

// routes/comercios.js
/**
 * @swagger
 * /api/comercios:
 *   get:
 *     summary: Lista todos os comércios
 *     tags: [Comércios]
 *     parameters:
 *       - in: query
 *         name: categoria
 *         schema:
 *           type: string
 *         description: Filtrar por categoria
 *     responses:
 *       200:
 *         description: Lista de comércios
 *         content:
 *           application/json:
 *             schema:
 *               type: array
 *               items:
 *                 $ref: '#/components/schemas/Comercio'
 */
router.get('/comercios', async (req, res) => {
    const { categoria } = req.query;
    const filtro = categoria ? { categoria } : {};
    const comercios = await Comercio.find(filtro);
    res.json(comercios);
});

Frameworks com suporte nativo ou bibliotecas: SpringDoc (Java), FastAPI (Python), NestJS (JavaScript), swagger-jsdoc (Node.js)

🔄 Versionamento de serviços - Criando APIs retrocompatíveis

Serviços se modificam e novas demandas surgem. Serviços estabelecem contratos de uso com seus clientes; mas e se precisamos alterá-los?

warning O problema: múltiplos clientes, diferentes versões

Imagine que sua API é consumida por:

  • 📱 Aplicação mobile (versão antiga e nova)
  • 💻 Web app (sempre atualizado)
  • 🔌 Integrações com parceiros (terceiros)

Se você modificar a API de forma quebrável (ex: renomear campo, remover endpoint), todos os clientes param de funcionar. O versionamento resolve esse problema.

Estratégias de versionamento

URL Versionamento na URL

Deixa evidente a versão utilizada. Fácil de criar regras de roteamento.

https://api.cidadevirtual.vercel.app/v1/comercios
https://v1.api.cidadevirtual.vercel.app/comercios

Vantagem: Visível, fácil cache, fácil roteamento
Desvantagem: "Polui" a URL

Query Versionamento via parâmetro

Adiciona um parâmetro de query indicando a versão.

https://api.cidadevirtual.vercel.app/comercios?version=1

Vantagem: Simples
Desvantagem: Pouco escalável, difícil roteamento

Header Versionamento via cabeçalho

Transferência por meio de metadados na requisição.

Accept-Version: v1
Accept: application/vnd.cidadevirtual+json;version=1.0

Vantagem: Flexível, URI limpa
Desvantagem: Menos visível, requer documentação

star Recomendação para o Cidade Virtual

Adotar versionamento na URL (ex: /v1/comercios) por ser mais simples, explícito e compatível com o ecossistema Vercel. Para mudanças que quebram compatibilidade, criar /v2 e manter /v1 funcionando por um período de transição (ex: 6 meses).

code Exemplo prático: Implementação de versionamento no Express

// server.js
const express = require('express');
const app = express();

// Versão 1 da API
const v1Router = express.Router();
v1Router.get('/comercios', (req, res) => {
    // Retorna comércios no formato original
    res.json({ version: 'v1', data: comerciosV1 });
});

// Versão 2 da API (com novos campos)
const v2Router = express.Router();
v2Router.get('/comercios', (req, res) => {
    // Retorna comércios com campos adicionais (ex: horario_expandido)
    res.json({ version: 'v2', data: comerciosV2 });
});

// Registrar versões
app.use('/v1', v1Router);
app.use('/v2', v2Router);

// Redirecionamento padrão para a versão mais recente
app.use('/api', (req, res) => {
    res.redirect(`/v1${req.url}`);
});

📏 Boas práticas de versionamento de APIs

looks_one Versionamento Semântico

Adote SemVer (MAJOR.MINOR.PATCH) para suas APIs: v1.2.3

  • MAJOR: Mudança que quebra compatibilidade
  • MINOR: Nova funcionalidade, compatível
  • PATCH: Correção de bug, compatível

timeline Depreciação gradual

Anuncie versões antigas como "deprecated" antes de removê-las.

  • Adicionar header Deprecation: true
  • Informar data de remoção: Sunset: "2026-12-31"
  • Manter versão antiga por pelo menos 6 meses

api Mudanças compatíveis (não quebram)

  • ✅ Adicionar novo endpoint
  • ✅ Adicionar campo opcional na resposta
  • ✅ Adicionar novo parâmetro com valor padrão
  • ❌ Remover campo existente
  • ❌ Renomear campo
  • ❌ Alterar tipo de dado

menu_book Documente o versionamento

Na documentação (Swagger/OpenAPI), deixe claro:

  • Qual versão está sendo documentada
  • Links para versões anteriores
  • Changelog de mudanças entre versões
  • Datas de depreciação planejadas

👥 Documentação de jornadas de usuário

Além da documentação técnica da API, é importante documentar as jornadas de usuário da aplicação, especialmente para projetos de extensão que envolvem a comunidade.

map Exemplo: Jornada do Comerciante no Cidade Virtual

1 Acessa o site e clica em "Registrar"
2 Preenche dados (nome, e-mail, senha, tipo: comerciante)
3 Confirma e-mail (envio de link)
4 Faz login com e-mail e senha
5 Acessa painel → "Cadastrar Comércio"
6 Preenche informações (nome, categoria, endereço, telefone)
7 Publica → comércio visível na busca
receipt Formatos recomendados para documentação de jornadas:
  • Histórias de usuário: "Como um comerciante, quero cadastrar meu negócio para que clientes me encontrem"
  • Diagramas de sequência UML para fluxos complexos
  • User journey maps com emoções e pontos de dor
  • Vídeos tutoriais para usuários com baixa familiaridade digital

🔁 Visão integradora - Proposta para o Cidade Virtual

1

Documentação da API com Swagger/OpenAPI

Criar arquivo openapi.yaml documentando todos os endpoints. Hospedar a documentação interativa via Swagger UI no endpoint /api/docs.

2

Documentação como código

Utilizar swagger-jsdoc para gerar documentação automaticamente a partir de comentários JSDoc nas rotas e controllers.

3

Versionamento da API

Adotar /v1/ nas URLs. Para futuras mudanças que quebrem compatibilidade, criar /v2/ e manter versão anterior por 6 meses.

4

Documentação de jornadas de usuário

Criar um manual do usuário em PDF com prints e passo a passo para comerciantes e moradores, disponível no site.
