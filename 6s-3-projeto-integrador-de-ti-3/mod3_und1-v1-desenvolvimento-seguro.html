🔐 O que é desenvolvimento seguro?

Construir software seguro exige ter o conhecimento básico dos princípios de segurança. O objetivo principal é manter a confidencialidade, integridade e disponibilidade (tríade CID) dos recursos de informação, permitindo operações bem-sucedidas do negócio.

⚠️ Entendendo riscos de segurança

Um risco de segurança ocorre quando um agente de ameaça interage com um sistema, no qual pode haver uma vulnerabilidade latente que pode ser explorada e causar um impacto.

local_car_wash Exemplo prático - Analogia do ladrão de carros

Um ladrão de carros (agente de ameaça) passa por um estacionamento verificando os carros presentes (o sistema), procurando por portas destrancadas (a vulnerabilidade). Quando a encontra, abre a porta (a exploração) e leva para si o que está dentro do carro (o impacto).

No Cidade Virtual: Um invasor (agente de ameaça) pode tentar acessar a API (sistema) procurando por endpoints sem autenticação (vulnerabilidade). Ao encontrar um, explora para extrair dados de comerciantes (impacto).

warning Falhas de segurança podem ser introduzidas em qualquer fase do ciclo de desenvolvimento:
  • 🔴 Não identificação das necessidades de segurança no início do projeto
  • 🔴 Arquiteturas com problemas de design
  • 🔴 Práticas de codificação ruins (ex: concatenação de SQL)
  • 🔴 Implantação de modo inapropriado (ex: debug ativo em produção)
  • 🔴 Inserção de vulnerabilidades durante manutenções
lightbulb Insight importante:

Na web, controles no cliente oferecem pouco ou nenhum benefício de segurança. Validações no front-end são úteis para experiência do usuário, mas nunca devem ser a única linha de defesa. Toda validação deve ser repetida no back-end.

📊 OWASP Top 10 - Os riscos mais críticos

O OWASP (Open Web Application Security Project) é uma organização sem fins lucrativos que mantém o Top 10, um documento que lista as vulnerabilidades mais críticas em aplicações web. *Uma nova versão está prevista para 2025.*

A1 Controle de Acesso Quebrado

Usuários acessam funcionalidades ou dados para os quais não têm permissão.

A2 Falhas Criptográficas

Dados sensíveis trafegados ou armazenados sem proteção adequada.

A3 Injeção (SQL, NoSQL, Command)

Dados não confiáveis enviados a um interpretador como parte de um comando.

A4 Design Inseguro

Falhas arquiteturais que comprometem a segurança do sistema.

A5 Configuração Incorreta de Segurança

Configurações padrão inseguras, mensagens de erro detalhadas em produção.

A6 Componentes Vulneráveis

Uso de bibliotecas ou frameworks com CVEs conhecidas.

A7 Falhas de Identificação e Autenticação

Senhas fracas, gerenciamento inadequado de sessão.

A8 Falhas de Integridade de Software e Dados

Atualizações ou dados sem verificação de origem/integridade.

A9 Falhas de Monitoramento e Log

Ausência de auditoria e detecção de incidentes.

A10 Falsificação de Requisição do Lado do Servidor

Servidor faz requisições não intencionadas para recursos internos/externos.

book Referência essencial

Consulte o OWASP Cheat Sheet Series (https://cheatsheetseries.owasp.org/) para guias práticos de como implementar cada controle de segurança.

🛡️ Recomendações práticas por camada

storage Infraestrutura

  • ✅ Usar criptografia nos dados em trânsito (TLS/HTTPS) e em repouso
  • ✅ Proteger ambientes internos (firewalls, redes privadas)
  • ✅ Não usar componentes com vulnerabilidades conhecidas (CVEs)
  • ✅ Isolar ambientes de desenvolvimento, homologação e produção

web Aplicação

  • ✅ Usar bibliotecas e dependências atualizadas (npm audit, snyk)
  • ✅ Considerar autenticação de múltiplos fatores (MFA) para administradores
  • ✅ Armazenar senhas com hashes seguros (bcrypt, Argon2)
  • ✅ Criar política de senhas (mínimo 8 caracteres, complexidade)
  • ✅ Proteger contra requisições exaustivas (rate limiting)
  • ✅ Fazer gestão efetiva da sessão de usuário (timeout, logout)

receipt_long Log e Auditing

  • ✅ Monitoramento e resposta a incidentes
  • ✅ Manter registros de acessos de usuários (quem, quando, o quê)
  • ✅ Rastreabilidade de ações/operações críticas (ex: exclusão de comércio)
  • ✅ Proteger logs contra alteração/exclusão

build Ferramentas

  • ✅ Usar ferramentas de testes de segurança (OWASP ZAP, Snyk)
  • ✅ Executar processos externos de auditoria
  • ✅ Realizar versionamento de projeto e código (Git)
  • ✅ Implementar SAST (análise estática) no pipeline CI/CD

api API

  • ✅ Adotar verificações de autorização em cada endpoint
  • ✅ Evitar expor dados em excesso (não retornar campos internos)
  • ✅ Tratar adequadamente dados das requisições (validação, sanitização)
  • ✅ Proteger contra ataques força-bruta (rate limiting, captcha)
  • ✅ Configurar adequadamente CORS (não usar * em produção)

error Erros e Exceções

  • ✅ Não expor stack traces em produção
  • ✅ Usar mensagens de erro genéricas para o usuário
  • ✅ Registrar detalhes internamente (logs)
  • ✅ Tratar exceções de forma consistente

🏙️ Aplicando segurança no Cidade Virtual

Com base nos princípios e recomendações apresentados, o projeto Cidade Virtual deve incorporar as seguintes práticas de segurança:

check_circle Controles já implementados ou planejados

  • Autenticação JWT com refresh token e tempo de expiração (1 hora para access token, 7 dias para refresh)
  • Bcrypt para hashing de senhas (fator de custo 10)
  • HTTPS obrigatório via Vercel (certificado automático)
  • Validação de entrada em todos os endpoints (express-validator)
  • Sanitização contra XSS e NoSQL Injection
  • Rate limiting no endpoint de login (5 tentativas em 15 minutos)
  • CORS restrito apenas para o domínio da aplicação front-end

code Exemplo prático - Middleware de autenticação no Cidade Virtual 

// middleware/auth.js
const jwt = require('jsonwebtoken');

const authMiddleware = (req, res, next) => {
    // 1. Obter token do header Authorization
    const authHeader = req.headers.authorization;
    if (!authHeader || !authHeader.startsWith('Bearer ')) {
        return res.status(401).json({ error: 'Token não fornecido' });
    }
    
    const token = authHeader.split(' ')[1];
    
    try {
        // 2. Verificar e decodificar token
        const decoded = jwt.verify(token, process.env.JWT_SECRET);
        
        // 3. Anexar usuário à requisição
        req.user = decoded;
        
        // 4. Verificar se o usuário tem permissão para acessar o recurso
        if (req.params.id && req.user.id !== req.params.id && req.user.tipo !== 'admin') {
            return res.status(403).json({ error: 'Acesso negado' });
        }
        
        next();
    } catch (error) {
        return res.status(401).json({ error: 'Token inválido ou expirado' });
    }
};

verified Exemplo prático - Validação e sanitização de entrada

// Validação com express-validator
const { body, validationResult } = require('express-validator');

const validarCadastro = [
    body('email').isEmail().normalizeEmail(),
    body('senha').isLength({ min: 8 }).trim(),
    body('nome').trim().escape(),
    body('tipo').isIn(['morador', 'comerciante', 'autonomo']),
    
    (req, res, next) => {
        const errors = validationResult(req);
        if (!errors.isEmpty()) {
            return res.status(400).json({ errors: errors.array() });
        }
        next();
    }
];

🔬 Testes de segurança

Para validar as práticas de segurança implementadas, devem ser realizados testes específicos:

speed Teste de força-bruta

Verificar se o rate limiting está funcionando: tentar login 10 vezes com senha errada em sequência.

bug_report Teste de injeção

Tentar inserir ' OR '1'='1 em campos de busca para testar proteção contra SQL/NoSQL injection.

code Teste de XSS

Tentar inserir <script>alert('XSS')</script> em campos que aceitam texto livre.

api Teste de autorização

Tentar acessar endpoint de outro usuário com token diferente (ex: morador tentando editar comércio de outro).

auto_awesome Ferramentas automatizadas recomendadas:
  • OWASP ZAP - Scanner de vulnerabilidades em aplicações web
  • Snyk - Verificação de vulnerabilidades em dependências (snyk test)
  • npm audit - Verificação nativa do Node.js para pacotes vulneráveis
  • ESLint com plugin de segurança - Análise estática para padrões inseguros

🔁 Visão integradora - Por onde começar?

Para incorporar desenvolvimento seguro no Cidade Virtual, siga estas etapas práticas:

1

Incorpore práticas de desenvolvimento seguro desde a concepção

Já nas fases iniciais, defina que a segurança é requisito não-funcional obrigatório, não um "plus".

2

Defina os requisitos de segurança no início

Ex: autenticação obrigatória para endpoints de escrita, tempo de sessão de 1 hora, etc.

3

Faça revisões e auditorias no projeto/código

Utilize checklists de segurança (como o OWASP ASVS) durante as inspeções de código.

4

Faça testes de segurança

Execute OWASP ZAP periodicamente e após cada alteração significativa.

5

Use ferramentas automatizadas

Integre npm audit e snyk ao pipeline de CI/CD (GitHub Actions).
