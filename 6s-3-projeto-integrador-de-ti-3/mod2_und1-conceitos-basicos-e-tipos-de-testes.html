🧪 O que é Teste de Software?

O teste de software é uma técnica de verificação dinâmica, ou seja, envolve a execução do programa (ou de partes dele) para avaliar seu comportamento real em comparação com o comportamento esperado especificado.

help_outline Três perguntas fundamentais
  1. O que devemos testar? → Priorização com base em risco e criticidade.
  2. Como podemos testar? → Estratégias: caixa branca, caixa preta, exploratório.
  3. O que esperar dos nossos testes? → Não garantem ausência de defeitos, mas reduzem riscos.
warning Atenção!

Testar exaustivamente (cobrir 100% das situações possíveis) é inviável em sistemas modernos, que podem ter milhares de componentes e infinitas combinações de entradas. O segredo está no planejamento estratégico e na priorização.

🎯 O que devemos testar? Priorização e Planejamento

Em um sistema como o Cidade Virtual, não é possível testar todas as combinações possíveis de entradas e cenários. Por isso, o planejamento é essencial.

real_estate_agent Exemplo Cidade Virtual - Priorização de Testes

Funcionalidades críticas (prioridade máxima):

  • ✅ Cadastro e autenticação de usuários (moradores, comerciantes, autônomos)
  • ✅ Busca por comércios e serviços (core do negócio)
  • ✅ Sistema de avaliações (confiança da comunidade)

Funcionalidades secundárias (prioridade média):

  • 📌 Mural de eventos e campanhas
  • 📌 Perfil do comerciante com horários diferenciados

Funcionalidades de baixo risco (prioridade baixa):

  • 🎨 Temas e personalização de interface
  • 📊 Relatórios estatísticos para administradores

Critério adotado: Funcionalidades com maior impacto direto no usuário e no modelo de negócio recebem mais testes.

insights Insight Avançado - Teste Baseado em Risco (Risk-Based Testing)

Priorize os testes com base em duas dimensões: probabilidade de falha e impacto da falha. Uma matriz de risco ajuda a decidir onde investir mais esforço.

Impacto \ Probabilidade Baixa Média Alta
Alto Teste médio Teste alto Prioridade crítica
Médio Teste baixo Teste médio Teste alto
Baixo Teste mínimo Teste baixo Teste médio

No Cidade Virtual: A falha no cadastro de comerciantes tem impacto alto e probabilidade média → prioridade alta. A falha no tema escuro tem impacto baixo e probabilidade baixa → teste mínimo.

🔍 Como podemos testar? Caixa Branca vs Caixa Preta

code

Teste Caixa Branca

Conhece o interior do artefato (código-fonte, estrutura interna).

  • Guiado pela estrutura lógica
  • Encontra erros (implementação incorreta)
  • Exige conhecimento técnico profundo
  • Exemplo: Testar todos os caminhos de uma função
Fluxo de controle
Cobertura de código
inventory_2

Teste Caixa Preta

Não conhece o interior do artefato, apenas as entradas e saídas esperadas.

  • Guiado por requisitos e contratos
  • Encontra falhas (comportamento não esperado)
  • Pode ser feito por quem não desenvolveu o código
  • Exemplo: Testar se a busca retorna resultados corretos
Documentação
Casos de uso

api Exemplo prático no Cidade Virtual

Teste caixa branca (unidade): Verificar se a função calcularAvaliacaoMedia([5,4,3]) realmente retorna 4.0, e se trata corretamente lista vazia e valores fora do intervalo.

Teste caixa preta (funcional): Verificar se o endpoint GET /api/comercios?categoria=alimentacao retorna apenas comércios da categoria "alimentação", conforme especificação do requisito RF23.

🧩 Testes Unitários

Testes unitários avaliam a menor parte testável do software (funções, métodos, classes). São a base da pirâmide de testes e devem ser rápidos, isolados e numerosos.

check_circle Características

  • ✅ Foco em caminhos lógicos (caixa branca)
  • ✅ Feitos pelo próprio desenvolvedor
  • ✅ Buscam alta cobertura de código (>70% é um bom alvo)
  • ✅ Capturam erros de lógica e regras de negócio
  • ✅ Executam em milissegundos

construction Ferramentas comuns

  • Jest (JavaScript/TypeScript) → Cidade Virtual
  • JUnit (Java)
  • PyTest (Python)
  • Mocha/Chai (Node.js)

code Exemplo de Teste Unitário com Jest - Cidade Virtual

// Função a ser testada (em services/avaliacaoService.js)
function calcularAvaliacaoMedia(avaliacoes) {
    if (!avaliacoes || avaliacoes.length === 0) return 0;
    const soma = avaliacoes.reduce((acc, nota) => acc + nota, 0);
    return soma / avaliacoes.length;
}

// Teste unitário com Jest (em __tests__/avaliacaoService.test.js)
describe('calcularAvaliacaoMedia', () => {
    test('deve calcular média correta para [5,4,3]', () => {
        expect(calcularAvaliacaoMedia([5,4,3])).toBe(4.0);
    });
    
    test('deve retornar 0 para lista vazia', () => {
        expect(calcularAvaliacaoMedia([])).toBe(0);
    });
    
    test('deve retornar 0 para null ou undefined', () => {
        expect(calcularAvaliacaoMedia(null)).toBe(0);
    });
    
    test('deve tratar notas decimais', () => {
        expect(calcularAvaliacaoMedia([4.5, 5.0, 3.5])).toBeCloseTo(4.333, 2);
    });
});

Resultado esperado: 4 testes passando, cobertura de 100% da função.

📐 Técnicas para Projeto de Testes Unitários

Para criar bons testes unitários, utilizamos técnicas sistemáticas que aumentam a eficácia na detecção de defeitos.

category 1. Partição por Classes de Equivalência

Objetivo: Dividir o domínio de entradas em classes/grupos com comportamento semelhante. Testa-se apenas um representante de cada classe.

Exemplo (Cidade Virtual): Validação de idade mínima para cadastro (18 anos).

  • Classe válida: idade ≥ 18
  • Classe inválida: idade < 18

Casos de teste: 25 anos (válido), 16 anos (inválido).

straighten 2. Análise de Valor Limite (Boundary Value Analysis)

Objetivo: Testar os limites entre as classes de equivalência, onde erros são mais frequentes.

Exemplo (validação de idade):

  • Limite inferior: 17, 18, 19
  • Limite superior (se houver, ex: 120): 119, 120, 121

No Cidade Virtual: Avaliação de comércios (notas de 0 a 5). Testar: -1, 0, 1, 4, 5, 6.

table_chart 3. Tabela de Decisão

Objetivo: Para cenários com múltiplas condições combinadas, a tabela de decisão ajuda a garantir cobertura de todas as combinações relevantes.

Exemplo (Cidade Virtual): Regra para exibir "selo de confiança" a um comércio.

Condições Caso 1 Caso 2 Caso 3 Caso 4
Avaliação média ≥ 4.5 V V F F
Mais de 10 avaliações V F V F
Selo de confiança Sim Não Não Não

sync_alt 4. Teste de Transição de Estados

Objetivo: Avaliar o comportamento de um sistema que pode estar em diferentes estados, com transições acionadas por eventos.

Exemplo (Cidade Virtual): Estados de um pedido de contato/negociação.

[Pendente] --(comerciante responde)--> [Em andamento] --(morador finaliza)--> [Concluído]
     |
     --(cancelamento)--> [Cancelado]

Testes: Verificar todas as transições possíveis, inclusive as inválidas (ex: tentar finalizar um pedido já cancelado).

🔗 Testes de Integração

Testes de integração verificam a interação entre componentes ou uma funcionalidade completa de modo separado da interface de usuário.

storage

Integração com Banco de Dados

Verificar se o repositório de usuários realmente persiste e recupera dados corretamente.

PostgreSQL
MongoDB
api

Integração com API Externa

Simular chamadas a serviços de geolocalização ou pagamento.

Mock
Stub

integration_instructions Exemplo no Cidade Virtual

Cenário: Testar se o endpoint POST /api/comercios insere corretamente os dados no banco e retorna o ID gerado.

// Teste de integração com Supertest + Jest
const request = require('supertest');
const app = require('../server');

describe('POST /api/comercios', () => {
    test('deve criar um novo comércio e retornar 201', async () => {
        const novoComercio = {
            nome: "Padaria do João",
            categoria: "alimentacao",
            endereco: "Rua das Flores, 123"
        };
        
        const response = await request(app)
            .post('/api/comercios')
            .send(novoComercio)
            .expect(201);
        
        expect(response.body).toHaveProperty('id');
        expect(response.body.nome).toBe("Padaria do João");
        
        // Verificar se realmente foi salvo no banco (consulta direta)
        const comercioSalvo = await db.query('SELECT * FROM comercios WHERE id = $1', [response.body.id]);
        expect(comercioSalvo.rows[0].nome).toBe("Padaria do João");
    });
});

Características: Mais lentos que testes unitários (acesso a banco/API), mais caros, menos frequentes.

🖥️ Testes de Sistema (End-to-End / E2E)

Testes de sistema simulam o uso real do sistema por usuários, normalmente automatizando a interface gráfica (UI) ou navegador.

warning Características importantes:
  • 🐌 Mais lentos (segundos a minutos por teste)
  • 💰 Mais caros de manter
  • 🔧 Mais frágeis (pequenas mudanças na UI quebram os testes)
  • 📊 Menos frequentes (executados em pipelines de CI/CD antes de releases)

cypress Exemplo com Cypress - Cidade Virtual

// cypress/integration/cadastro_comerciante.spec.js
describe('Cadastro de Comerciante', () => {
    beforeEach(() => {
        cy.visit('/registrar');
    });

    it('deve permitir cadastro de novo comerciante', () => {
        cy.get('input[name="nome"]').type('Mercearia do Zé');
        cy.get('select[name="tipo"]').select('comerciante');
        cy.get('input[name="email"]').type('ze@mercearia.com');
        cy.get('input[name="senha"]').type('senha123');
        cy.get('button[type="submit"]').click();
        
        // Verificar redirecionamento e mensagem de sucesso
        cy.url().should('include', '/dashboard');
        cy.contains('Bem-vindo, Mercearia do Zé').should('be.visible');
    });
    
    it('deve exibir erro para email já cadastrado', () => {
        // Cenário de email duplicado
        cy.get('input[name="email"]').type('ze@mercearia.com');
        cy.get('button[type="submit"]').click();
        cy.contains('Email já cadastrado').should('be.visible');
    });
});

Ferramentas comuns: Cypress, Selenium, Playwright, Puppeteer.

📊 Pirâmide de Testes (Mike Cohn)

A pirâmide de testes é um modelo que recomenda a proporção ideal entre os tipos de testes para um projeto equilibrado, rápido e confiável.

🔝 E2E / Sistema (poucos, lentos, caros)
🔄 Integração (médios, menos frequentes)
🧩 Unitários (muitos, rápidos, baratos)

Fonte: Adaptado de Cohn (2009)

trending_up Para o Cidade Virtual (projeto solo)

  • ⬤ 70-80% testes unitários (regras de negócio, validações, cálculos) → rápidos e fáceis de escrever
  • ⬤ 15-20% testes de integração (API + banco de dados) → validam a parte mais crítica
  • ⬤ 5-10% testes E2E (fluxos principais: cadastro, busca, avaliação) → garantem que o sistema funciona como um todo

Ferramentas sugeridas: Jest (unitário/integração), Supertest (integração de API), Cypress (E2E).

🚀 Outros tipos de testes (além da pirâmide)

security Teste de Segurança

Verifica vulnerabilidades: injeção SQL, XSS, autenticação quebrada, etc. Ferramentas: OWASP ZAP, Snyk.

speed Teste de Carga e Stress

Avalia comportamento sob alta demanda. Ex: 1000 usuários simultâneos no Cidade Virtual. Ferramenta: K6, JMeter.

checklist Teste de Aceitação

Validado com os representantes da comunidade (Lucia Matos e Roseane Soares). Verifica se o sistema atende aos critérios de negócio.

devices Teste de Usabilidade

Avalia facilidade de uso, especialmente para público com baixa familiaridade digital. Observação direta do usuário.

map Roadmap de Implementação de Testes (projeto solo)

  1. Semana 1: Configurar Jest e escrever testes unitários para as funções de validação (email, CPF, cálculo de média).
  2. Semana 2: Adicionar testes de integração para os endpoints principais (cadastro, busca, avaliação) com banco de dados de teste.
  3. Semana 3: Implementar testes E2E para os dois fluxos críticos (cadastro de comerciante e busca por categoria) com Cypress.
  4. Semana 4: Convidar Lucia Matos e Roseane Soares para testes de aceitação e usabilidade, documentando feedbacks.

Dica para projeto solo: Comece pelos testes unitários (baixo custo, alto retorno) antes de investir em testes E2E complexos. A cobertura de código é uma métrica amiga, mas não obsessão – priorize as partes críticas.
