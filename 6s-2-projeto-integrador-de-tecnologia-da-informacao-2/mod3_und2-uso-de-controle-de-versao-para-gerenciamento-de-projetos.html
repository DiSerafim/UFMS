📌 O que é Controle de Versão e por que ele é essencial?

Controle de versão é um sistema que registra alterações em um arquivo ou conjunto de arquivos ao longo do tempo, permitindo que você recupere versões específicas mais tarde. Em desenvolvimento de software, é uma ferramenta indispensável para trabalho em equipe, rastreabilidade e segurança do código.

❌ Sem controle de versão

  • Arquivos com nomes como: projeto_final_v2_versao_final_real_3.js
  • Conflitos frequentes ao compartilhar código por email ou USB
  • Perda de histórico: não se sabe quem alterou o quê e quando
  • Dificuldade de reverter código quebrado sem perder dias de trabalho

✅ Com Git (controle de versão moderno)

  • Histórico completo de todas as alterações
  • Trabalho colaborativo simultâneo (branches)
  • Rastreabilidade: quem, quando e por que cada linha foi alterada
  • Possibilidade de reverter para qualquer estado anterior do projeto
💡 No projeto Cidade Virtual: Utilizamos Git desde o início, com repositório no GitHub. Cada nova funcionalidade (ex: busca por categoria, cadastro de eventos) foi desenvolvida em uma branch separada, garantindo que a versão principal (main) sempre permanecesse estável.

🌿 Branches no Git: Desenvolvimento paralelo e organizado

Branches (ramos) são ramificações no código que permitem o desenvolvimento de novas funcionalidades, correções de bugs ou experimentos sem impactar a versão principal. Facilitam o trabalho em equipe e a integração de novas funcionalidades de forma isolada.

📊 Diagrama de branches (visualização típica): 
      main ──●─────────────●──────────●──────────●──────────▶
               \          /          /          /
      develop   ●────────●──────────●──────────●──────────▶
                 \      /          /          /
      feature/auth ●───●──────────●──────────●──────────▶
                    \ /          
      feature/crud   ●──────────●──────────▶
📌 Principais tipos de branches em um projeto Git:
  • main (ou master): Branch principal, sempre estável. Contém a versão de produção (ou pronta para deploy).
  • develop: Branch de integração. Funcionalidades concluídas são mescladas aqui antes de irem para main.
  • feature/* (ex: feature/busca, feature/login): Branches para desenvolvimento de novas funcionalidades. Cada feature tem sua própria branch.
  • hotfix/*: Correções urgentes em produção. São criadas a partir da main e, após correção, mescladas de volta.
  • release/*: Preparação para uma nova versão (últimos ajustes, testes, documentação).
Comandos básicos para trabalhar com branches: 
# Criar uma nova branch (e mudar para ela)
git checkout -b feature/nova-funcionalidade

# Listar todas as branches
git branch -a

# Mudar para uma branch existente
git checkout develop

# Mesclar (merge) uma branch na branch atual
git merge feature/nova-funcionalidade

# Excluir uma branch que não é mais necessária
git branch -d feature/nova-funcionalidade
🌿 No projeto Cidade Virtual (MERN): Adotamos o modelo Git Flow simplificado. Criamos branches feature/cadastro-usuario, feature/busca-comercios, feature/mural-eventos. Cada branch foi desenvolvida isoladamente e, após testes, mesclada na branch develop. Periodicamente, a develop era mesclada na main para gerar uma nova versão estável.

⚠️ Resolução de conflitos: como o Git lida com mudanças simultâneas

Quando dois ou mais desenvolvedores alteram o mesmo arquivo e as mesmas linhas de código, pode ocorrer um conflito durante a mesclagem (merge). O Git não consegue decidir automaticamente qual versão manter e pede intervenção manual.

📌 Cenário comum de conflito:

Desenvolvedor A modifica a linha 15 do CardComercio.js para adicionar um botão. Desenvolvedor B modifica a mesma linha 15 para corrigir um texto. Ambos desenvolvem em branches diferentes e tentam mesclar na develop. O Git sinaliza o conflito.

Exemplo de marcação de conflito no arquivo: 
<<<<<<< HEAD
const mensagem = 'Clique para ver detalhes';
=======
const mensagem = 'Ver mais informações do comércio';
>>>>>>> feature/nova-funcionalidade
Passos para resolver um conflito:
  1. Abra o arquivo conflitante em um editor.
  2. Localize as marcações <<<<<<< HEAD, ======= e >>>>>>> feature/....
  3. Decida qual versão manter ou faça uma versão híbrida (removendo as marcações).
  4. Salve o arquivo.
  5. Adicione o arquivo resolvido: git add arquivo.js.
  6. Finalize o merge: git commit.
🔧 Ferramentas que ajudam na resolução: Editores como VS Code e IDEs como WebStorm possuem interface visual para resolver conflitos. Ferramentas externas como meld e KDiff3 também são muito úteis.
✅ Boa prática para evitar conflitos frequentes:
  • Faça commits pequenos e frequentes.
  • Sincronize com o repositório remoto diariamente (git pull --rebase).
  • Comunique seu time sobre quais arquivos você está modificando em cada branch.
  • Divida responsabilidades: evite que duas pessoas alterem o mesmo arquivo simultaneamente.
  • Use rebase (git rebase develop) antes de mesclar uma branch de feature.

🚀 DevOps: Integração entre desenvolvimento e operações

DevOps (Development + Operations) é um conjunto de práticas que integra desenvolvimento de software e operações de TI para entregar software de forma contínua, confiável e ágil. O controle de versão é a espinha dorsal do DevOps, pois rastreia cada mudança e viabiliza a automação dos pipelines de entrega.

Princípios fundamentais do DevOps:
  • Cultura de colaboração: Desenvolvedores e equipes de operações trabalham juntos durante todo o ciclo de vida do software.
  • Automatização: Processos manuais são substituídos por scripts e pipelines automatizados.
  • Monitoração e feedback contínuo: Sistemas são monitorados em produção, e problemas geram alertas e melhorias.
  • Infraestrutura como código (IaC): Servidores, bancos de dados e redes são configurados via código versionado (ex: Terraform, Ansible).

🔴 Antes do DevOps

  • Entregas manuais e pouco frequentes (a cada meses)
  • Equipes isoladas: dev "joga código por cima do muro" para ops
  • Rollback lento e arriscado
  • Ambientes de desenvolvimento e produção diferentes

🟢 Com DevOps (CI/CD)

  • Entregas automáticas e frequentes (várias vezes ao dia)
  • Colaboração e responsabilidade compartilhada
  • Rollback rápido via Git (reverter commit)
  • Ambientes replicáveis: dev = homologação = produção

🔄 Integração Contínua (CI) – Testando automaticamente cada mudança

Integração contínua é uma prática de desenvolvimento onde os desenvolvedores mesclam suas alterações no repositório principal várias vezes ao dia. Cada mesclagem dispara uma construção (build) e uma suíte de testes automatizados, garantindo que o código continue funcionando.

Fluxo típico de CI:
  1. Desenvolvedor cria uma branch feature/nova-funcionalidade.
  2. Desenvolve e faz commits na branch local.
  3. Ao finalizar, abre um Pull Request (PR) no GitHub/GitLab.
  4. Automaticamente, o servidor de CI (ex: GitHub Actions, GitLab CI, Jenkins) dispara:
    - Build do projeto
    - Execução de testes unitários e de integração
    - Verificação de estilo de código (lint)
  5. Se todos os testes passarem, o PR pode ser revisado e mesclado.
  6. Se falharem, a equipe é notificada para corrigir.
Exemplo de arquivo de configuração do GitHub Actions (CI para Cidade Virtual): 
# .github/workflows/ci.yml
name: CI - Cidade Virtual

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
        with:
          node-version: 18
      - run: npm install
      - run: npm test
      - run: npm run build
💡 Benefícios da CI: Reduz falhas de integração, detecta erros precocemente (minutos após o commit), aumenta a confiança da equipe e melhora a qualidade do software.

📦 Entrega Contínua (CD) – Software pronto para deploy a qualquer momento

Entrega contínua é a extensão natural da Integração Contínua. Ela garante que todo o código aprovado nos testes esteja em um estado implantável a qualquer momento. O deploy em produção pode ser manual (apertar um botão) ou totalmente automático (Continuous Deployment).

Diferenças entre entrega contínua e deploy contínuo:
  • Continuous Delivery (CD): O software é automaticamente construído, testado e preparado para produção, mas o deploy em produção é manual (acionado por um humano). Ideal para times que precisam de aprovação de negócio antes de lançar.
  • Continuous Deployment (CD auto): Cada mudança que passa pelos testes vai automaticamente para produção. Usado por empresas como Netflix, Amazon, Etsy.
Como o controle de versão habilita a CD:
  • Cada commit na branch main (após CI bem-sucedida) gera um artefato (docker image, pacote npm, .exe).
  • O artefato é versionado (tag Git) e armazenado em registro (ex: Docker Hub, GitHub Packages).
  • O pipeline de CD faz o deploy automático desse artefato em ambiente de homologação e, após validação, em produção.
  • Rollback é simples: basta reverter o commit e reexecutar o pipeline.
🚀 Para o futuro da Cidade Virtual (Módulo 4): Poderemos configurar CI/CD com GitHub Actions para automatizar os testes a cada Pull Request e, após aprovação, fazer o deploy automático da aplicação React no Vercel/Netlify e do backend Node.js no Render/Fly.io.

⚠️ Desafios comuns no uso de controle de versão e como superá-los

🌿 Gerenciamento eficiente de branches em projetos grandes

Desafio: Em equipes grandes, dezenas de branches ativas podem causar confusão. Solução: Adote modelos como Git Flow ou GitHub Flow, mantenre nomeclatura padronizada (ex: feature/..., hotfix/...), e exclua branches já mescladas.

⚠️ Resolução de conflitos frequentes

Desafio: Em times com alta concorrência de código, conflitos são constantes. Solução: Faça commits pequenos, sincronize várias vezes ao dia, comunique-se com a equipe e use git rebase antes do merge.

📝 Manutenção de um histórico limpo e bem documentado

Desafio: Mensagens de commit genéricas ("fix", "update", "código bugado") dificultam rastreabilidade. Solução: Adote Conventional Commits (feat: add busca, fix: corrige login) e use ferramentas de análise de histórico.

🔐 Segurança e autenticação

Desafio: Tokens de acesso, senhas e chaves de API não devem ser versionadas no Git. Solução: Use arquivos .env adicionados ao .gitignore e utilize segredos do GitHub/Docker para configurações de deploy.

✅ Boas práticas de versionamento para o Projeto Cidade Virtual

📌 Estrutura de branches adotada no projeto:
  • main: Versão estável sempre pronta para deploy.
  • develop: Integração das features concluídas.
  • feature/crud-comercios: Desenvolvimento isolado.
  • feature/autenticacao-jwt: Desenvolvimento isolado.
  • feature/mural-eventos: Desenvolvimento isolado.
  • hotfix/cors-error: Correção urgente em produção.
📝 Padrão de mensagens de commit (Conventional Commits): 
feat: adiciona busca por categoria de comércios
fix: corrige erro de autenticação no login
docs: atualiza README com instruções de instalação
test: adiciona testes unitários para o componente CardComercio
chore: atualiza dependências do backend
refactor: simplifica lógica de filtro na home
🔄 Fluxo completo adotado:
  1. Criar branch a partir de develop: git checkout -b feature/nova-feature
  2. Desenvolver com commits pequenos e mensagens semânticas.
  3. Atualizar branch local com develop (rebase): git fetch origin develop && git rebase develop
  4. Enviar para o GitHub: git push origin feature/nova-feature
  5. Abrir Pull Request (PR) no GitHub solicitando revisão.
  6. CI (GitHub Actions) executa testes automaticamente.
  7. Após aprovação, fazer merge na develop (ou squash + merge).
  8. Excluir branch da feature (local e remota).

📌 Conclusão da unidade

O controle de versão é fundamental para equipes de desenvolvimento, desde projetos individuais até grandes corporações com centenas de desenvolvedores. Ferramentas como Git permitem colaboração eficiente e segura, rastreabilidade total e a capacidade de reverter alterações a qualquer momento.

Além disso, o DevOps utiliza o controle de versão como base para automatizar a entrega de software, por meio de práticas como Integração Contínua e Entrega Contínua (CI/CD), que reduzem falhas e aceleram o tempo de lançamento de novas funcionalidades.

Principais aprendizados desta unidade:

  • ✅ O que são branches e como organizar o desenvolvimento paralelo

  • ✅ Relação entre Git, DevOps, CI e CD
  • ✅ Desafios comuns e boas práticas para manter o repositório organizado
