Objetivos da unidade

  • Compreender a importância da análise de requisitos para desenvolvimento de software
  • Conhecer técnicas para levantar, documentar e priorizar requisitos
  • Aplicar metodologias ágeis na definição de MVP e no planejamento de soluções

O que são requisitos?

Requisitos são descrições das funcionalidades e restrições de um software. Eles representam o que o sistema deve fazer e sob quais condições. A engenharia de requisitos é a área da engenharia de software responsável por levantar, documentar, analisar e gerenciar esses requisitos ao longo do projeto.

📌 Requisitos Funcionais

Definem o que o sistema deve fazer. São as funcionalidades, comportamentos e tarefas específicas que o software precisa executar. Exemplos: "O sistema deve permitir cadastro de usuários", "O sistema deve calcular o frete com base no CEP".

📌 Requisitos Não Funcionais

Definem restrições sobre como o sistema deve funcionar. Estabelecem critérios de qualidade, segurança, desempenho, usabilidade, confiabilidade, portabilidade, etc. Exemplos: "O sistema deve responder em menos de 2 segundos", "O sistema deve suportar 1000 usuários simultâneos".

💡 Importante: Requisitos mal levantados são a principal causa de falha em projetos de software. Um requisito ambíguo, incompleto ou contraditório pode gerar retrabalho e insatisfação do cliente.

Técnicas para levantamento de requisitos

🎤 Entrevistas

Conversas individuais com stakeholders (usuários, clientes, gerentes) para entender suas necessidades, dores e expectativas. Podem ser estruturadas (com roteiro fixo) ou semiestruturadas (com perguntas abertas).

📋 Questionários

Aplicados a um grande número de pessoas para coletar dados quantitativos e qualitativos. São úteis para validar hipóteses com uma amostra representativa do público-alvo.

👀 Observação direta

O analista observa o usuário realizando suas tarefas no ambiente real de trabalho. Ajuda a identificar necessidades implícitas que o usuário nem sempre consegue descrever em palavras.

🧠 Brainstorming

Sessões criativas em grupo para gerar ideias, funcionalidades e soluções. Incentiva a participação de todos e pode revelar requisitos inovadores.

📄 Análise de documentos

Estudo de manuais, formulários, regulamentos, sistemas legados e outros artefatos que podem conter requisitos implícitos ou explícitos.

🔍 Prototipação

Construção de versões simplificadas do sistema (protótipos de baixa ou alta fidelidade) para validar requisitos com os usuários antes do desenvolvimento completo.

📌 Dica prática: No Projeto Integrador, combine pelo menos duas técnicas. Exemplo: entrevistas para entender a fundo a dor do usuário e questionários para validar com mais pessoas as funcionalidades propostas.

Documentação de requisitos

📄 Documento de Visão

Apresenta uma visão geral do projeto, o problema que será resolvido, o público-alvo, os objetivos e as principais funcionalidades (alto nível). É o primeiro documento a ser elaborado.

📋 Especificação de Requisitos de Software (ERS)

Documento detalhado que lista todos os requisitos funcionais e não funcionais de forma estruturada, geralmente em tópicos numerados. Serve como contrato entre a equipe de desenvolvimento e o cliente.

📖 Histórias de Usuário (User Stories)

Formato ágil para descrever requisitos, geralmente seguindo o modelo: "Eu, como [papel do usuário], quero [ação] para [benefício]". Exemplo: "Eu, como morador, quero buscar comércios por categoria para encontrar serviços rapidamente".

🔀 Diagramas de Caso de Uso

Representação gráfica (UML) que mostra os atores (usuários) e os casos de uso (funcionalidades) do sistema. Ajuda a visualizar quem faz o quê no sistema.

📖 Conexão com a prática: No seu Projeto Integrador, você pode começar com o Documento de Visão, depois listar os requisitos numerados (ERS) e complementar com histórias de usuário. Isso já é um excelente nível de detalhamento para o módulo 1.

Priorização de requisitos

Nem todos os requisitos podem (ou devem) ser implementados na primeira versão. A priorização ajuda a equipe a focar no que realmente agrega valor ao usuário e ao negócio.

📊 Método MoSCoW

Uma das técnicas mais populares de priorização, que classifica os requisitos em quatro categorias:

  • M (Must have - Obrigatório): Essencial para o sistema funcionar. Sem ele, o projeto não faz sentido. Ex: cadastro de usuários.
  • S (Should have - Deveria ter): Importante, mas não crítico. Pode ser contornado temporariamente. Ex: recuperação de senha.
  • C (Could have - Poderia ter): Desejável, agrega valor, mas sua ausência não inviabiliza o sistema. Ex: tema escuro (dark mode).
  • W (Won't have - Não terá agora): Fica para versões futuras. Reconhecidamente útil, mas fora do escopo atual.
🎯 Matriz de Valor vs Esforço

Classifica os requisitos em uma matriz 2x2, cruzando o valor entregue ao usuário com o esforço de implementação. Prioriza-se o que dá mais valor com menos esforço.

📋 Backlog priorizado

No Scrum e outras metodologias ágeis, o Product Owner mantém uma lista ordenada (backlog) onde os itens mais importantes ficam no topo. A cada sprint, a equipe puxa os itens mais prioritários.

✅ Exercício prático: Liste 10 requisitos do seu projeto Cidade Virtual. Classifique cada um como M, S, C ou W (MoSCoW). Os primeiros 3-5 da lista M são seu MVP.

Metodologias ágeis e MVP

🚀 O que é MVP (Produto Mínimo Viável)?

MVP é a versão mais simples de um produto que ainda pode ser entregue aos usuários para gerar aprendizado e feedback. Não é um produto "incompleto" ou "mal feito" – é a versão com apenas as funcionalidades essenciais (Must have) para resolver o problema central.

🔄 Ciclo Construir-Medir-Aprender (Lean Startup)

O MVP é construído rapidamente, entregue a um grupo piloto de usuários, que fornecem feedback. A equipe aprende com esse feedback, ajusta as hipóteses e constrói a próxima versão. Esse ciclo se repete até que o produto atenda bem às necessidades dos usuários.

📅 Scrum e Sprints

No Scrum, o desenvolvimento é dividido em iterações curtas (sprints), geralmente de 1 a 4 semanas. A cada sprint, a equipe entrega um incremento de produto potencialmente utilizável. O backlog é constantemente refinado e repriorizado.

💡 Kanban

Método visual de gestão de fluxo de trabalho, baseado em um quadro com colunas (Ex: "A fazer", "Fazendo", "Teste", "Pronto"). Limita a quantidade de trabalho em andamento (WIP) para evitar gargalos.

🚀 Para o seu Projeto Integrador II: Seu MVP pode ser a versão da Cidade Virtual com cadastro de comércios, busca por categoria e mural de eventos. Sem notificações push, sem chat, sem relatórios avançados – isso fica para versões futuras.

Planejamento de soluções: do problema ao código

📌 Etapa 1: Definição do problema (Unidade 1)

Já vimos: identificar a dor real do usuário, o contexto, quem sofre e por que isso importa. Ex: "Moradores não encontram comércios locais; comerciantes não têm visibilidade".

📌 Etapa 2: Levantamento de requisitos

Aplicar técnicas (entrevistas, questionários, observação) para entender o que o sistema precisa fazer. Listar requisitos funcionais e não funcionais.

📌 Etapa 3: Priorização e definição do MVP

Usar MoSCoW ou outra técnica para separar o obrigatório (MVP) do desejável. Definir o escopo da primeira entrega.

📌 Etapa 4: Documentação

Registrar os requisitos em formato acessível (documento de visão, ERS, histórias de usuário). Compartilhar com stakeholders para validação.

📌 Etapa 5: Modelagem e prototipação

Construir diagramas (caso de uso, classes, DER) e protótipos de tela (baixa ou alta fidelidade) para visualizar a solução antes de codificar.

📌 Etapa 6: Planejamento de iterações

Dividir o desenvolvimento em sprints (se usar Scrum) ou em tarefas no quadro Kanban. Estimar esforço e definir prazos realistas.

📌 Etapa 7: Codificação, testes e entrega

Implementar as funcionalidades priorizadas, testar (unitário, integração, aceitação) e entregar aos usuários piloto para feedback.

📌 Resumo do fluxo: Problema → Requisitos → Priorização (MVP) → Documentação → Modelagem → Planejamento → Codificação/Testes → Entrega → Feedback → Iteração.

Exemplo prático: aplicando no Projeto Cidade Virtual

🎓 Contexto real (Cabanagem/PA)

Problema já definido: Moradores e comerciantes desconhecem os negócios e serviços disponíveis no próprio bairro, fragilizando a economia local.

📋 Requisitos funcionais (parciais):
  • RF01 - O sistema deve permitir cadastro de usuários com perfis (morador, comerciante, autônomo).
  • RF02 - O sistema deve permitir que comerciantes criem e editem seu perfil público (nome, descrição, categoria, endereço, contato).
  • RF03 - O sistema deve permitir que moradores busquem comércios por categoria (alimentação, reparos, beleza, etc.).
  • RF04 - O sistema deve permitir que moradores busquem comércios por proximidade (CEP ou bairro).
  • RF05 - O sistema deve exibir um mural com eventos e campanhas comunitárias.
  • RF06 - O sistema deve permitir que moradores avaliem comércios (nota de 1 a 5).
📋 Requisitos não funcionais (parciais):
  • RNF01 - A interface deve ser responsiva (acessível em celulares).
  • RNF02 - O sistema deve ter tempo de resposta inferior a 2 segundos nas buscas.
  • RNF03 - O sistema deve seguir diretrizes de acessibilidade (contraste, HTML semântico).
📊 Priorização (MoSCoW) para o MVP:
  • Must (MVP): RF01, RF02, RF03, RF05 (cadastro, perfil do comércio, busca por categoria, mural).
  • Should: RF04 (busca por proximidade), RF06 (avaliações).
  • Could: sistema de notificações, chat entre morador e comerciante.
  • Won't (agora): relatórios avançados, integração com redes sociais.

MVP definido: Versão 1.0 da Cidade Virtual com cadastro de usuários, perfil de comércio, busca por categoria e mural de eventos. Isso já resolve o problema central (visibilidade e conexão) e pode ser entregue em 4-6 semanas.

Desafios comuns na análise de requisitos

⚠️ Escopo mal definido (scope creep)

Stakeholders pedem novas funcionalidades durante o desenvolvimento, expandindo o escopo original. Solução: priorização clara (MoSCoW), documentação assinada e processo formal de mudança.

⚠️ Requisitos ambíguos ou incompletos

Exemplo: "sistema rápido" – o que é rápido? 1 segundo? 5 segundos? Solução: requisitos devem ser específicos, mensuráveis, atingíveis, relevantes e testáveis (SMART).

⚠️ Conflitos entre stakeholders

Um grupo quer uma funcionalidade, outro grupo quer outra. Solução: workshops de alinhamento, priorização baseada em valor e, se necessário, decisão do sponsor ou Product Owner.

⚠️ Mudanças frequentes de requisitos

Especialmente em projetos longos. Solução: metodologias ágeis (Scrum, Kanban) abraçam mudanças, desde que priorizadas no backlog.

✅ Boa prática: Valide seus requisitos com os usuários antes de começar a programar. Mostre o documento, os protótipos, faça perguntas. É muito mais barato corrigir um requisito no papel do que no código já escrito.

Síntese da unidade

A análise de requisitos é a ponte entre o problema identificado (Unidade 1) e a solução construída. Nesta unidade, vimos que:

  • Requisitos são descrições do que o sistema deve fazer (funcionais) e como deve se comportar (não funcionais).
  • Técnicas como entrevistas, questionários, observação e prototipação ajudam a levantar requisitos de forma estruturada.
  • Documentar requisitos (Documento de Visão, ERS, histórias de usuário) é essencial para comunicação com a equipe e stakeholders.
  • Priorizar requisitos (MoSCoW, matriz valor vs esforço) evita desperdício e foca no que realmente importa para o MVP.
  • Metodologias ágeis (Scrum, Kanban, Lean Startup) ensinam a construir, medir e aprender com versões incrementais do produto.
  • O planejamento de soluções segue um fluxo: problema → requisitos → priorização → documentação → modelagem → codificação → testes → entrega → feedback → iteração.
💬 Pergunta norteadora (reflita e depois leve para o fórum):

Com base no problema que você identificou no seu contexto (ou no exemplo da Cidade Virtual), liste os 5 requisitos funcionais mais importantes. Qual deles é o verdadeiro coração do seu MVP? Por quê?
