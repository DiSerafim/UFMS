✅ Verificação, Validação e Teste (VV&T) na Cidade Virtual

Verificação: Avalia se o produto está sendo construído corretamente (segundo especificações). Validação: Avalia se o produto correto está sendo construído (atende às necessidades do usuário). Teste: Execução do software para encontrar defeitos.

📋 Verificação (estática)

  • Revisões de código (Code Review): Todo Pull Request é revisado por outro membro (simulado em projeto individual por auto-revisão criteriosa).
  • Análise estática (Linting): ESLint + Prettier configurados no pré-commit (Husky).
  • Testes unitários: Validam funções isoladamente (ex: validação de email).

🎯 Validação (dinâmica)

  • Testes de integração: Validam a interação entre componentes (ex: API + MongoDB).
  • Testes end-to-end (E2E): Simulam usuário real (ex: busca por comércio).
  • Testes de aceitação: Realizados com um grupo piloto de comerciantes (feedback sobre usabilidade).
📊 Pirâmide de testes aplicada:
  • Base (muitos): 35+ testes unitários (Jest) – funções de validação, helpers, models.
  • Meio (alguns): 12 testes de integração (supertest + MongoDB in-memory) – rotas da API.
  • Topo (poucos): 4 testes end-to-end (Playwright) – fluxos críticos (login, busca, cadastro).
📈 Métricas de cobertura obtidas:
  • Cobertura de statements: 87%
  • Cobertura de branches: 79%
  • Cobertura de funções: 91%
  • Cobertura de linhas: 86%

🧪 Tipos de testes realizados

check_box Testes Unitários

Ferramenta: Jest + React Testing Library.
Exemplo: Validação de email, formatação de datas, funções de cálculo.
Quantidade: 35 testes.
Resultado: 100% passando.

api Testes de Integração

Ferramenta: Supertest + MongoDB Memory Server.
Exemplo: Rota POST /api/comercios com autenticação JWT.
Quantidade: 12 testes.
Resultado: Todos os endpoints principais cobertos.

web Testes End-to-End (E2E)

Ferramenta: Playwright (Chromium, Firefox, WebKit).
Exemplo: Buscar "padaria" → clicar no primeiro resultado → ver detalhes.
Quantidade: 4 cenários críticos.
Resultado: 100% passando nos 3 navegadores.

speed Testes de Desempenho

Ferramenta: K6 (script local).
Cenário: 100 usuários simultâneos buscando comércios.
Resultado: Latência p95 < 300ms, sem erros.

security Testes de Segurança

Ferramenta: OWASP ZAP (análise passiva) + npm audit.
Verificações: Vulnerabilidades em dependências, headers de segurança, injeção SQL.
Resultado: Nenhuma vulnerabilidade crítica.

people Testes de Usabilidade

Método: Teste com 5 comerciantes do bairro Cabanagem.
Feedback: Interface intuitiva, mas solicitaram "modo escuro" e "salvar busca".
Ação: Adicionado ao backlog para Módulo 4 (se possível).

⚠️ Desafios enfrentados na aplicação de VV&T e soluções adotadas

1. Testes frágeis (flaky tests)

Desafio: Testes E2E falhavam intermitentemente devido a timeouts (rede, carregamento assíncrono).
Solução: Aumento de timeouts seletivos, uso de waitFor com condições explícitas, e execução em headless mode com retries (Playwright).

2. Dependências externas no teste de integração

Desafio: Testes de API que dependiam do MongoDB externo (lentos e não isolados).
Solução: Adoção do MongoDB Memory Server (banco em memória) para cada teste, garantindo isolamento e velocidade.

3. Cobertura de código ilusória

Desafio: Alta cobertura (95%) com testes que não verificavam comportamento real (apenas chamavam funções).
Solução: Revisão manual dos testes, adição de asserts significativos e exclusão de testes "fakes".

4. Ambiente de teste diferente de produção

Desafio: Testes passavam localmente, mas falhavam no GitHub Actions (variáveis de ambiente, versões de Node).
Solução: Containerização com Docker para replicar ambiente, e uso de GitHub Secrets para variáveis.

💡 Lição aprendida: Testes automatizados não substituem a revisão humana. Um teste que passa sem validar a saída correta é pior do que nenhum teste.

📌 Importância de VV&T para a qualidade e confiabilidade

No contexto da Cidade Virtual, a aplicação de VV&T foi fundamental para garantir que a plataforma atendesse às expectativas dos moradores e comerciantes do bairro Cabanagem. Os principais benefícios observados foram:

  • Redução de bugs em produção: Antes dos testes automatizados, bugs demoravam dias para serem descobertos. Agora, falhas são detectadas em minutos (via CI).
  • Maior confiança para refatorar: Com uma suíte de testes robusta, foi possível reescrever partes do código (ex: lógica de busca) sem medo de quebrar funcionalidades existentes.
  • Documentação viva do sistema: Os testes funcionam como uma especificação executável do comportamento esperado (ex: "se usuário não autenticado tentar criar comércio, deve receber 401").
  • Feedback rápido para desenvolvedores: O pipeline de CI (GitHub Actions) executa todos os testes em menos de 3 minutos, permitindo correções imediatas.
  • Credibilidade com os usuários: Comerciantes relataram que "o sistema não travou" e "as informações sempre aparecem corretamente" – resultado direto dos testes de integração e E2E.
📊 Métrica objetiva: A taxa de defeitos em produção (bugs por mil requisições) caiu 76% após a implementação da suíte de testes completa.
