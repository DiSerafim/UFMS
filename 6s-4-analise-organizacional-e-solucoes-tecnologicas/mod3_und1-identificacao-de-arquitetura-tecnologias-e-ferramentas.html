🏛️ 1. Projeto de Arquitetura de Software

book Conceito segundo Sommerville (2018, p.148)

"Projeto de arquitetura visa compreender como um sistema de software deve ser organizado e projetar a estrutura geral desse sistema"

A arquitetura de software é a espinha dorsal de qualquer sistema. Ela define:

  • 📐 Estrutura: Como os componentes do sistema se organizam
  • 🔄 Interações: Como os componentes se comunicam
  • 📏 Restrições: Regras e padrões que guiam o projeto
  • 🎯 Decisões estratégicas: Escolhas que impactam desempenho, segurança e manutenibilidade
insights Por que a arquitetura é tão importante?

Uma boa arquitetura reduz custos de manutenção, facilita a evolução do sistema, permite reuso de componentes e garante atributos de qualidade como desempenho, segurança e escalabilidade. Uma má arquitetura pode inviabilizar um projeto promissor.

📐 2. Estilos Arquiteturais

Estilos arquiteturais são modelos de referência que orientam a organização do sistema. Conheça os quatro principais:

layers

Arquitetura em Camadas (Layered Architecture)

📝 Descrição: Sistema organizado em camadas hierárquicas, cada uma com funcionalidades específicas. Cada camada fornece serviços para a camada superior e utiliza serviços da camada inferior.

┌──────────────────────────────┐                    
│     Camada de Apresentação   │  (UI/React/Angular)
├──────────────────────────────┤                    
 │    Camada de Negócio (API)   │(Node.js/Spring Boot) 
├──────────────────────────────┤                     
 │  Camada de Persistência (DB) │  (PostgreSQL/MongoDB)
└──────────────────────────────┘

✅ Quando utilizar:

  • Adicionar novos recursos sobre sistemas existentes
  • Desenvolvimento dividido entre diferentes equipes (cada uma foca em uma camada)
  • Necessidade de segurança em múltiplos níveis
  • Sistemas corporativos e aplicações web tradicionais
✅ Vantagens:
  • Camadas podem ser substituídas desde que mantenham a mesma interface
  • Separação de responsabilidades
  • Favorece manutenção e evolução incremental
  • Reutilização de funcionalidades comuns
⚠️ Desvantagens:
  • Separação nem sempre clara entre camadas
  • Interações diretas entre camadas distantes podem ser necessárias
  • Desempenho prejudicado por múltiplos níveis de interpretação
  • Risco de "camada de panaceia" (tudo misturado)
storage

Arquitetura em Repositório (Repository Architecture)

📝 Descrição: Os dados do sistema ficam em um repositório central. Componentes não interagem diretamente, apenas por meio do repositório central.

        ┌──────────┐     ┌──────────┐
        │Componente│     │Componente│
        │    A     │     │    B     │
        └────┬─────┘     └────┬─────┘
             │                │      
             ▼                ▼      
        ┌─────────────────────────┐
          │  REPOSITÓRIO CENTRAL    │  
          │  (Banco de Dados / DB)  │  
        └─────────────────────────┘
             ▲                ▲      
             │                │      
        ┌────┴─────┐     ┌────┴─────┐
        │Componente│     │Componente│
        │    C     │     │    D     │
        └──────────┘     └──────────┘

✅ Quando utilizar:

  • Volume de dados a serem armazenados por longos períodos
  • Sistemas dirigidos por dados, onde atualizações disparam ações
  • Ferramentas CASE e ambientes de desenvolvimento integrado
  • Sistemas de informação corporativos (ERP, CRM)
✅ Vantagens:
  • Dados centralizados e consistentes
  • Componentes podem ser independentes
  • Facilidade para adicionar novos componentes que acessam os mesmos dados
  • Backup e segurança centralizados
⚠️ Desvantagens:
  • Repositório se torna ponto único de falha e gargalo de desempenho
  • Acoplamento de componentes ao esquema do repositório
  • Dificuldade de evolução do esquema de dados
  • Concorrência e locking podem ser complexos
devices

Arquitetura em Cliente-Servidor (Client-Server Architecture)

📝 Descrição: Sistema dividido entre clientes (que fazem requisições) e servidores (que fornecem serviços). Cada serviço pode ser executado em um servidor separado.

        ┌─────────┐         ┌─────────┐
        │ Cliente │◄───────►│ Servidor│
        │  (Web)  │   HTTP  │  (API)  │
        └─────────┘         └────┬────┘
                                 │     
        ┌─────────┐              ▼     
        │ Cliente │         ┌─────────┐
        │ (Mobile)│◄───────►│  Banco  │
        └─────────┘   SQL   │  Dados  │
                            └─────────┘

✅ Quando utilizar:

  • Acesso a dados compartilhados de diferentes locais
  • Variação de carga (servidores podem ser replicados)
  • Sistemas web, aplicações móveis, microsserviços
  • Aplicações com lógica de negócio centralizada
✅ Vantagens:
  • Servidores podem ser distribuídos em rede
  • Funcionalidade centralizada acessível a todos os clientes
  • Clientes mais leves (thin clients)
  • Escalabilidade horizontal por replicação de servidores
⚠️ Desvantagens:
  • Cada serviço é um ponto único de falha
  • Desempenho depende da rede e do servidor
  • Sobrecarga de comunicação (latência, banda)
  • Gerenciamento de estado pode ser complexo
filter_alt

Arquitetura em Duto e Filtro (Pipe and Filter)

📝 Descrição: Os dados fluem (como em um duto/pipeline) de um componente (filtro) para outro, sendo processados sequencialmente. Cada filtro transforma os dados e passa adiante.

        Dados ──►│ Filtro A │──►│ Filtro B │──►│ Filtro C │──► Resultado
        Brutos   (limpeza)     (análise)      (formatação)

✅ Quando utilizar:

  • Processamento de dados em etapas (ETL - Extract, Transform, Load)
  • Sistemas de processamento de fluxo contínuo (streaming)
  • Compiladores e processamento de linguagens
  • Análise de logs e pipelines de dados
✅ Vantagens:
  • Fácil de entender e permite o reuso de transformações
  • Evolução por meio da adição de novos filtros é direta
  • Pode ser sequencial ou concorrente (paralelismo de dados)
  • Isolamento de responsabilidades
⚠️ Desvantagens:
  • Formato dos dados deve ser acordado entre todos os filtros
  • Processamento paralelo pode gerar sobrecarga de comunicação
  • Difícil reusar componentes com estruturas de dados incompatíveis
  • Pode haver latência acumulativa

📊 3. Comparação entre Estilos Arquiteturais

Critério Camadas Repositório Cliente-Servidor Duto e Filtro
Acoplamento Baixo (entre camadas) Médio (todos ao repositório) Médio (clientes ao servidor) Baixo (filtros independentes)
Escalabilidade Vertical Limitada Horizontal (servidores) Horizontal (paralelização)
Desempenho Pode ser prejudicado Gargalo no repositório Depende da rede Latência acumulativa
Manutenibilidade Alta Média Média Alta
Segurança Multi-nível Centralizada No servidor Por filtro

⚖️ 5. Como Escolher a Arquitetura Ideal?

insights Critérios de decisão

  • 🔹 Natureza do problema: Processamento de dados (duto)? Interação com usuário (camadas)? Dados compartilhados (repositório)?
  • 🔹 Escalabilidade esperada: Quantos usuários? Volume de dados? Carga variável?
  • 🔹 Restrições de desempenho: Latência aceitável? Throughput necessário?
  • 🔹 Equipe e expertise: Quais tecnologias o time domina?
  • 🔹 Orçamento e prazo: Arquiteturas mais complexas exigem mais tempo e recursos.
  • 🔹 Segurança e conformidade: LGPD, dados sensíveis, níveis de acesso.

apartment Aplicação prática - Projeto "Vias da Cabanagem" (Belém/PA)

Para o dashboard de monitoramento participativo de infraestrutura urbana, uma arquitetura Cliente-Servidor + Repositório é ideal:

  • Frontend (Camada Apresentação): React com Leaflet para mapas interativos
  • Backend (Camada Negócio): Node.js + Express para API REST
  • Repositório: PostgreSQL (dados estruturados) + MongoDB (reportes colaborativos)
  • Pipeline de dados: Python + pandas para ETL dos dados públicos (SINISA)
  • Hospedagem: Servidor cloud (AWS ou Vercel) para garantir disponibilidade

Essa combinação atende aos requisitos de escalabilidade (crescimento do bairro), segurança (dados geolocalizados) e manutenibilidade (evolução contínua).
